# hh-search

Автопоиск вакансий на hh.ru для личного использования. Регулярно обходит
курируемые листинги, отсеивает нерелевантное, оценивает оставшееся по профилю
и выгружает только новые находки в CSV и Markdown.

Дизайн: [`docs/superpowers/specs/2026-07-27-hh-autosearch-design.md`](docs/superpowers/specs/2026-07-27-hh-autosearch-design.md)

## Быстрый старт

```bash
mkdir -p data/config data/state data/reports data/logs
cp config.example/*.yaml data/config/
$EDITOR data/config/app.yaml     # укажите свой contact_email

# uid контейнера обязан совпадать с владельцем ./data, иначе запись в том
# отказывает: bind-mount подменяет каталог образа вашим вместе с владельцем.
printf 'HH_UID=%s\nHH_GID=%s\n' "$(id -u)" "$(id -g)" >> .env

docker compose build
docker compose run --rm hh-search init-db
docker compose run --rm hh-search run
docker compose up -d
```

Отчёты появятся в `data/reports/`, логи — в `data/logs/hh.log`. Проверить, что
запись в том действительно работает: после `init-db` файл `data/state/hh.db`
обязан существовать и принадлежать вам.

Правку `contact_email` пропустить нельзя: заглушка `your-email@example.com`
отвергается на старте, потому что домен зарезервирован под примеры (RFC 2606) и
письмо туда не дойдёт. Адрес уезжает в `User-Agent` и служит hh.ru единственным
способом связаться с нами вместо того, чтобы забанить, — раньше первый запуск с
неотредактированным файлом завершался `ok`, отправив десяток запросов с
несуществующим контактом.

Если uid всё-таки не совпал, сервис не отдаёт трейсбек, а называет причину и
действие одной строкой:

```
нет доступа к каталогу данных /data/state (база hh.db): unable to open database
file. процесс работает от uid=10001 gid=10001, а /data/state принадлежит
uid=1000 gid=1000. ... Приведите HH_UID/HH_GID в .env к владельцу ./data ... и
пересоздайте контейнер: docker compose up -d --force-recreate
```

Совет выбирается по факту: если владелец каталога совпадает с вашим uid, текст
скажет про права каталога (`chmod`) или про том, смонтированный `:ro`, — потому
что правка `HH_UID` там не лечит ничего. Развёрнутое объяснение ловушки с uid
лежит в [`.env.example`](.env.example) — файле, который вы копируете в `.env`.

## Источник данных

Публичный API hh.ru для соискателей закрыт (403; поддержка прекращена 15.12.2025).
Поиск через RSS невозможен: `robots.txt` hh.ru запрещает правилом `Disallow: *?*`
любой URL с query-строкой, а RSS-поиск — это `/search/vacancy/rss?text=...`.
Используются курируемые листинги `/vacancies/{slug}` и `?page=N` (последний разрешён
явным `Allow: /vacancies/*?page=`) плюс блок JSON-LD `JobPosting` со страницы
вакансии. Авторизация, куки и эмуляция браузера не применяются.

Ограничение источника: листинг отдаёт 20 вакансий на страницу и не умеет
фильтровать по региону или опыту — всё это делает локальный фильтр по заголовку.
Узких slug'ов у hh.ru нет: `/vacancies/yocto` молча отдаёт общий индекс, поэтому
свои slug'и стоит проверить одним GET перед первым прогоном.

## Режим работы с hh.ru

Соблюдаются: честный `User-Agent` с контактным адресом, `robots.txt`, одно
соединение за раз с паузой между запросами, `Retry-After` и экспоненциальный
backoff. Устойчивый `403` останавливает прогон — обходные пути не применяются.
Описание каждой вакансии скачивается ровно один раз за всё время.

Про `robots.txt` честно: используется **собственный матчер RFC 9309**, а не
`urllib.robotparser` из stdlib. Причина не в эстетике — stdlib не поддерживает
подстановочные знаки (`RuleLine.applies_to` это `startswith`), поэтому правила
`Disallow: *?*` он не видит вовсе и разрешает запрещённое. Свой матчер понимает
`*` и `$`, сверяет путь вместе с query-строкой, при конфликте выбирает правило с
самым длинным шаблоном и перепроверяет правила после каждого редиректа. Если
`robots.txt` недоступен или не разобрался — запрещено всё.

hh.ru отвечает на `/vacancies/{slug}` редиректом 302 на региональный поддомен
(`nn.hh.ru` и подобные) по геолокации IP. Своими считаются `hh.ru` и его
поддомены; `robots.txt` кэшируется по origin, поэтому у поддомена спрашиваются
его собственные правила. `hh.kz`, `rabota.by` и `hh.uz` своими **не** считаются:
это другие сайты со своими правилами и своей нумерацией вакансий.

## Настройка

| Файл | Что менять |
|---|---|
| `data/config/queries.yaml` | Набор листингов (`slug`), кластеры, веса, число страниц |
| `data/config/profile.yaml` | Сигналы, веса скоринга, стоп-слова, порог |
| `data/config/app.yaml` | Расписание, троттлинг, потолки объёма прогона, пути, контактный email |
| `.env` | `HH_UID`/`HH_GID` — см. [`.env.example`](.env.example) |

Опечатка в конфиге роняет процесс на старте с указанием поля — это сделано
намеренно, включая опечатки в значениях (границы у всех чисел) и повторные
ключи YAML.

### Сколько прогон себе позволяет

Секция `app.limits` в `app.yaml` — предохранитель, а не оптимизация. Умолчания
подобраны так, чтобы штатный режим их не заметил (на образцовом конфиге прогон
делает 9 запросов к листингам и до 60 к страницам вакансий), но знать про ручки
стоит заранее:

| Ключ | Умолчание | Что ограничивает |
|---|---|---|
| `listing_pages_per_run` | 60 | Сумму `pages` по всем листингам, то есть число запросов за выдачей |
| `enrich_per_run` | 200 | Число запросов к страницам вакансий за один прогон |
| `rows_per_batch` | 500 | Сколько строк выборка поднимает в память при отчёте и пересчёте |

Сумма `pages` сверяется с потолком **при загрузке конфига**: 50 листингов по 20
страниц — это 20 990 запросов к hh.ru и 5.8 часа одних только пауз вежливости,
и раньше такой конфиг принимался молча. Конфиг, у которого одни паузы длиннее
`schedule.interval_hours`, тоже отвергается на старте — иначе демон работает
встык. Работа сверх потолка не теряется: её берёт следующий прогон.

Второй половиной той же страховки служит `mem_limit: 256m` в `compose.yaml`:
лимит не мешает штатной работе (запас к измеренному пику примерно
четырёхкратный — замер записан там же, рядом с ключом), но превращает
разрастание выборки в перезапуск одного контейнера вместо OOM-killer'а,
выбирающего жертву на всём хосте.

### Как писать сигналы

Пять правил, каждое — следствие устройства матчера, а не вкуса. Нарушение
первых четырёх даёт сигнал, который **молча не срабатывает**: он не роняет
загрузку, не пишет в лог и просто не приносит вакансий.

1. **Кириллический сигнал задаётся ОСНОВОЙ, а не словом.** Русские слова
   склоняются, и матчер дописывает окончание сам — но только к тому, что вы
   написали. `ведущий` не найдёт «ведущего разработчика», `старший` не найдёт
   «Старшего инженера». Пишите `ведущ`, `старш`, `архитектур`, `проектирован`.
   Латинские сигналы, наоборот, ищутся точной формой: `armv` не работает как
   префикс — он не совпадёт ни с `ARMv7`, ни с `ARMv8`, ни с `ARM64`, а совпадёт
   ровно со словом `armv`, которого в вакансиях не пишут. Нужны `armv7` и `armv8`
   по отдельности. У матча по основе есть минимальная длина в три символа —
   иначе `с` и `по` выкашивали бы половину выдачи.
2. **Справа за сигналом не должно быть буквы или цифры.** `arm` не найдёт
   `ARM64`, `python` не найдёт `python3`, `llm` не найдёт `LLMs`, `node` не
   найдёт `Node.js`, `iot` не найдёт `IIoT` (там мешает ещё и буква слева).
   Все нужные формы перечисляйте явно — так и сделано в
   `config.example/profile.yaml`.
3. **Многословный сигнал не терпит дефис вместо пробела и наоборот.**
   `team lead` не найдёт `Team-Lead`, а `код-ревью` не найдёт «код ревью».
   Если встречаются оба написания — вносите оба.
4. **Не используйте короткие латинские сигналы из похожих букв.** Матчер
   схлопывает визуально одинаковые буквы кириллицы и латиницы (без этого
   стоп-слово `1С` не срабатывало бы на `1C`), поэтому латинский `c`
   совпадает с русским предлогом «с», а `co` — с «со»: ложное срабатывание
   на каждой второй вакансии. Пишите `c++`, `c/c++` или `си`.
5. **Перечисленные написания одной сущности собирайте в ГРУППУ** — вложенным
   списком: `[arm, arm64, armv7, armv8]`. Правила 2 и 3 заставляют
   перечислять написания, а насыщение считает сигналы, и без группы одна
   архитектура, упомянутая всеми четырьмя написаниями, весила бы столько же,
   сколько четыре разные технологии. Группа — один сигнал насыщения и один
   штраф, сколько бы её написаний ни совпало. Простая строка остаётся
   группой из одного элемента, поэтому старые профили не переписываются.

И про стоп-слова: ложное срабатывание стоит вакансии до ближайшей правки
конфига — она уходит в `rejected` и вернётся оттуда следующим прогоном, только
если конфиг изменился. Общее слово в этом списке опаснее, чем кажется:
`оператор` отбраковывал «Ведущий разработчик в крупный оператор связи», то есть
ровно целевой телеком. Пишите узко: `оператор пк`, `оператор колл`.

## Команды

```bash
docker compose run --rm hh-search run          # разовый прогон
docker compose run --rm hh-search init-db      # создать схему (первый запуск)
docker compose run --rm hh-search healthcheck  # свежесть последнего прогона
docker compose run --rm hh-search report --since 7d  # перегенерировать отчёт
docker compose run --rm hh-search mark 12345 applied
docker compose up -d                           # демон: serve по расписанию
```

`serve` — точка входа контейнера: спит и раз в `schedule.interval_hours`
вызывает тот же прогон, что и `run`.

**Про `docker stop` без иллюзий.** Флаг остановки проверяется МЕЖДУ прогонами,
поэтому цена зависит от того, во что вы попали:

| Когда остановили | Сколько ждать | Код возврата |
|---|---|---|
| Демон спит между прогонами | доли секунды (замер: 0.28 с) | 0 |
| Идёт прогон, и он успевает закончиться за `stop_grace_period` | столько, сколько осталось прогону | 0 |
| Идёт прогон, и он не успевает | весь `stop_grace_period` (по умолчанию 30 с), потом SIGKILL | 137 |

Согласовать `stop_grace_period` с длительностью прогона нельзя: её потолок
задан `app.limits` и при умолчаниях (60 + 200 запросов с паузой 1 с) составляет
не меньше 260 секунд, а сверху ограничен лишь интервалом между прогонами. Так
что 137 здесь — не поломка, и искать в нём проблему не надо: уже сделанное не
теряется на любом исходе. Каждая вакансия закоммичена своим оператором, а
строку журнала, брошенную убитым процессом, закрывает следующий прогон. Если
остановка обязана быть быстрой — останавливайте между прогонами либо поднимите
`stop_grace_period` под свой `app.limits`.

Одновременно работает ровно один прогон: `docker exec … run` во время работы
`serve` получит «прогон уже идёт» и код 1. Замок — файл `hh.db.lock` рядом с
базой; его снимает ядро, поэтому убитый контейнер ничего после себя не
запирает. Без замка два прогона задваивали отчёт: дедупликация приёмника —
чтение-правка-запись по файлу дня, и она гонится.

Про `healthcheck` без иллюзий: он падает, если последний **успешный** прогон
старше двух интервалов, и это индикатор для того, кто смотрит. Docker (в отличие
от Swarm) контейнер по `unhealthy` **не перезапускает** — `restart: unless-stopped`
реагирует только на выход процесса. Прогон считается успешным при статусе `ok`
или `partial` (частичная потеря работы). `failed` — там, где работы не сделано
вовсе, и таких исходов четыре:

- источник не отдал ни одной из запрошенных страниц листинга (полная потеря
  сети, недоступный `robots.txt`, блокировка);
- страницы листинга отданы, но вакансий не найдено ни одной;
- страницы вакансий отданы, но не разобрана ни одна — так выглядит смена
  вёрстки hh.ru;
- ни один приёмник не принял непустой отчёт (например, том `/data/reports`
  смонтирован не туда).

Иначе и полная потеря сети, и смена вёрстки, и сутки без единого файла отчёта
выглядели бы для healthcheck успехом — а очередь тем временем безвозвратно
уходила бы в `enrich_failed`.

Устойчивый `403` (два подряд) останавливает демон, но `restart: unless-stopped`
перезапускает контейнер на любом коде возврата, поэтому одной остановки мало.
`serve` пишет `/data/state/access-forbidden.stop`, и пока файл на месте, в сеть
не идёт **ни одна** команда — ни `serve`, ни `run`. Проверка стоит на обеих
дверях сознательно: пока она жила только в `serve`, предохранитель открывался
самым естественным действием человека — увидев остановленный демон, он делает
`run` («а сейчас как?») и получает полный обход листингов. Разберитесь и удалите
файл руками. Одиночный `403` на одной странице прогон не роняет — он бывает
антиботом на конкретном запросе.

Ещё один предохранитель против лишних запросов: прогон, начатый раньше, чем
через половину `schedule.interval_hours` после предыдущего **успешного**,
**пропускается** — к hh.ru не уходит ничего (в лог уходит строка с тем, через
сколько минут прогон снова возможен). Без этого `docker restart` немедленно
запускал полный обход листингов, и обычная возня с конфигом («поправил профиль
— перезапустил»)
стоила десятков лишних обходов за вечер. Пропуск не сдвигает срок следующего
прогона, поэтому пауза не может вырасти больше чем в полтора интервала — то
есть предохранитель не способен сам по себе покрасить healthcheck.

Вакансию, «умершую» на скачивании (`rejected` / `enrich_failed`), возвращает в
работу `mark <id> new`: команда обнуляет счётчик попыток и чистит причину
отказа. Если понизить `enrich.max_attempts`, уже потраченные попытки становятся
чрезмерными задним числом — такие вакансии считает счётчик `run.stalled`, и
прогон об этом кричит.

## Разработка

```bash
uv sync --frozen --extra dev
uv run pytest                # без сети
uv run pytest -m network     # контрактные тесты против живого hh.ru
uv run ruff check . && uv run ruff format --check . && uv run mypy hh_search tests
```

`uv pip install --system ".[dev]"` не сработает: системный интерпретатор Ubuntu
помечен externally-managed (PEP 668). Тот же набор проверок гоняет CI
(`.github/workflows/ci.yml`).

Контрактные тесты — ранняя система оповещения: если hh.ru изменит разметку
листинга, уберёт JSON-LD или перепишет `robots.txt`, они об этом скажут. В CI не
запускаются, чтобы сборка не зависела от живой выдачи; при отсутствии сети
пропускаются, а не падают.

Часть тестов сторожит не код, а **документ**: `tests/test_spec_matches_code.py` и
четыре теста в `tests/test_config_example.py` сверяют с фактом инвентарь модулей,
ориентир размера файлов, DDL, образцы конфигов, образец `compose.yaml`, оценку
объёма прогона, набор команд CLI и таблицу фикстур. Заведены они не для красоты:
финальное ревью ветки обнаружило, что разошлись с кодом РОВНО те разделы спеки,
которых не сторожил ни один тест, а все сторожимые оказались безупречными. Если
такой тест покраснел — правьте документ вместе с кодом, а не выключайте сторожа.
