# Приёмник `telegram` — дизайн

Дата: 2026-07-29. Статус: согласован владельцем, к реализации.

Документ описывает ОДИН новый компонент. Действующее описание системы целиком —
`2026-07-27-hh-autosearch-design.md`; здесь только то, что к нему добавляется, и
только те его решения, которые новый компонент обязан соблюсти.

## §0. Откуда взялась задача

Первый живой прогон против hh.ru состоялся 2026-07-29 (прогон `id=3`, статус
`partial`): найдено 160, новых 120, отсеяно 22, обогащено и отправлено 98.
Отчёт `data/reports/2026-07-29-new.md` — 16.4 КБ, 134 строки. Владелец хочет
получать результат прогона в личный приватный канал Telegram, а не ходить за
ним на машину.

Решения владельца, принятые в этом обсуждении:

- В канал уходит «Топ» сообщением и полный отчёт файлом.
- Файл — **HTML, не markdown**: телефон не открывает `.md` браузером, и ссылки
  в нём остаются текстом. Кликабельность ссылок — требование, а не удобство.
- Первая цель — увидеть, что информация доходит. Богатство формата вторично.

## §1. Границы

Делается: приёмник `telegram` в существующей точке расширения `Sink` (транспорт
вынесен в `sinks/telegram_client.py`, приёмник — в `sinks/telegram_sink.py`:
разделение принято владельцем в Task 3, чтобы оба модуля уложились в бюджет
§4.3 основной спеки без строки-исключения), рендер
HTML-отчёта, отправка сообщения и файла, сторожа.

Не делается: команды бота (канал односторонний, бот только пишет), отметка
статуса вакансии из Telegram, отдельный порог для канала, ретрай отправки
внутри прогона. Последнее — сознательно: следующий прогон повторит отправку сам,
см. §5.

## §2. Что уходит в канал

Два обращения к Bot API на прогон, в этом порядке.

**Сообщение** (`sendMessage`): строка со счётчиками отчёта, затем «Топ» —
вакансии с баллом не ниже `profile.report_threshold`, каждая ссылкой на hh.ru,
с компанией, регионом, зарплатой и баллом.

Счётчики именно отчёта, а не прогона: протокол `Sink.emit(vacancies, now)` не
получает `RunStats` и получать не должен — иначе ради одной строки текста
пришлось бы менять интерфейс, общий с `csv` и `markdown`. Поэтому в шапке
стоит то, что приёмнику известно: сколько вакансий дописано этим прогоном и
сколько из них выше порога. Читателю это и нужнее, чем `discovered`/`rejected`.

В «Топ» сообщения идут только вакансии, ДОПИСАННЫЕ этим прогоном, — то есть
прошедшие дедупликацию §5, а не весь «Топ» файла дня. Иначе второй прогон суток
повторил бы в канале то, что владелец уже прочитал утром, и повторял бы это
все шесть раз в день. Файл при этом остаётся полным (§6): сообщение — про
«что нового», файл — про «что есть».

`parse_mode=HTML`, а не `MarkdownV2`. Причина фактическая: `MarkdownV2` требует
экранировать `_ * [ ] ( ) ~ \` > # + - = | { } . !`, и хотя бы один из этих
символов есть практически в каждом заголовке вакансии живого прогона («Team
Lead Go (Golang, продукты для управления инфраструктурой и PKI (TLS/ГОСТ)»,
«Backend Developer senior/middle+ (Node.js/Nest)»). В HTML-режиме экранируются
ровно три символа — `&`, `<`, `>`, — и набор разрешённых тегов (`<b>`, `<i>`,
`<a href>`, `<code>`) покрывает нужное.

Потолок `sendMessage` — 4096 символов. Сообщение строится с проверкой длины: не
влезающие позиции «Топа» отбрасываются, а вместо них дописывается строка «ещё N
— в файле». Молчаливого обрезания быть не должно: 5 позиций из 98 сегодня
укладываются с запасом, но порог — настройка, и однажды не уложатся.

Одинокая позиция, чей ПОЛНЫЙ рендер (заголовок, компания, регион, зарплата)
сам не влезает в потолок вместе с шапкой и хвостом «ещё N», не превращается в
ноль показанных записей при честном «ещё 1»: `render_message`
(`sinks/telegram_message.py`) пробует запасной, заведомо короткий вариант —
голую ссылку с усечённым заголовком, без метаданных. Заголовок усекается
ИСХОДНЫМ текстом, до экранирования и до сборки тега `<a>`: обратный порядок
рвёт тег или именованную сущность (`&amp;` пополам) и даёт `400 can't parse
entities` у Bot API вместо честного «Топа». Длина ищется двоичным поиском —
корректно, потому что экранирование не укорачивает текст. Если не влезает
даже пустой заголовок (практически недостижимо: ссылка и оценка сами по себе
короткие), поведение остаётся прежним — только хвост про файл, без записи.

**Файл** (`sendDocument`): `<ГГГГ-ММ-ДД>-new.html` из `data/reports`. Потолок
файла у Bot API — 50 МБ, потолок подписи — 1024 символа; при 98 вакансиях в
день файл занимает единицы сотен килобайт, то есть запас четырёхзначный.

## §3. Куда встраивается

Точка расширения существует с самого начала: докстринг `Sink` в
`hh_search/sinks/base.py` гласит «сюда позже встанет TelegramSink». Новый
приёмник реализует тот же протокол — `name` и `emit(vacancies, now) -> int`,
где возвращается число ЗАПИСАННЫХ, а не отданных (см. §5).

Регистрация — в `build_sinks` (`hh_search/sinks/__init__.py`) рядом с `csv` и
`markdown`. Имя в конфиге — `telegram`.

К `api.telegram.org` идёт обычный `httpx`. Вежливый клиент из
`sources/http.py` не годится и не должен использоваться: он проверяет
`robots.txt` и держит паузу `delay_between_requests_sec` под hh.ru. Применять
его к Telegram означало бы и бессмысленную проверку чужого `robots.txt`, и
паузу вежливости там, где вежливость измеряется иначе.

Рендер HTML — отдельная чистая функция, принимающая вакансии и возвращающая
строку. Отдельная потому, что её надо тестировать без сети и без Telegram, а
позже она же обслужит файловый приёмник `html`, если он понадобится. Сам
приёмник `html` сейчас НЕ делается (YAGNI): файл пишет `telegram`, потому что
именно ему есть что отправлять.

## §4. Секреты

`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` читаются из окружения. Не из YAML:
`.env` уже в `.gitignore`, уже приезжает в контейнер через `env_file` в
`compose.yaml`, и держать пароль бота в конфиге рядом с профилем поиска — значит
однажды его закоммитить. `chat_id` приватного канала отрицателен
(вид `-100…`), знак — часть идентификатора.

Отсутствие или пустота любой из двух переменных — **отказ на старте**, кодом
`EXIT_CONFIG`, до всякой сети. Это обязательство §7 основной спеки: о дефекте
конфигурации человек узнаёт до первого запроса, а не в середине прогона.
Механически это выполняется само: `build_sinks` вызывается из `_sinks()` до
`start_run()` (контракт задачи 9), и поднятая им `ValueError` уже превращается
в `EXIT_CONFIG`.

**Токен не попадает в логи.** У Bot API он лежит в ПУТИ URL
(`/bot<ТОКЕН>/sendMessage`), а проект логирует URL при отказах — то есть первая
же сетевая ошибка утащила бы пароль бота в `data/logs/hh.log`, файл, который
человек первым делом кому-нибудь показывает. Поэтому текст любой ошибки этого
приёмника строится по ИМЕНИ МЕТОДА (`sendMessage`, `sendDocument`), а URL в него
не подставляется никогда. Сторожится тестом (§7).

## §5. Дедупликация и отказ

`emit_to_sinks` (`pipeline/reporting.py`) ловит исключение любого приёмника,
записывает его в `failed` и не теряет вакансии. Но следом, в `report()`, есть
существенное для нас поведение: **при отказе ЛЮБОГО приёмника вакансии не
помечаются отправленными** (ранний возврат сразу за вызовом `_complain`) и
целиком приезжают в следующий прогон.

Файловые приёмники это переживают, потому что дедуплицируют по содержимому
файла дня. Приёмник без такой защиты выдал бы в канал дубль всякий раз, когда
упал сосед. Поэтому `telegram` дедуплицирует **тем же способом и по тому же
принципу**: файл дня `<дата>-new.html` читается перед записью, уже
присутствующие в нём вакансии считаются отправленными, `emit` возвращает число
дописанных. Дубль внутри ОДНОЙ пачки (два элемента `vacancies` с одним `url` в
одном вызове) закрыт тем же приёмом, что у `CsvSink.emit`: множество `already`
растёт по ходу цикла, а не сравнивается только с файлом.

**Читаются файлы `LOOKBACK_DAYS` предыдущих суток, а не только вчерашних.**
Одних текущих не хватает, и это не край, а штатный исход: ключ дедупликации —
имя файла с датой, то есть он новый каждые сутки, а `mark_reported` при отказе
не вызывался. Прогон 23:50 с упавшим `send_document` (или с упавшим
соседом-`csv`) оставляет вакансии непомеченными; прогон 03:50 следующих суток
не находит файла новых суток, считает вакансии новыми и **дословно повторяет
вечернее сообщение**. При `interval_hours: 4` любой вечерний отказ попадает в
это окно.

Одних вчерашних суток мало: если следующая попытка довозки (см. ниже) ТОЖЕ
упадёт, вакансия остаётся непомеченной ещё одни сутки, и прогон через двое
суток после исходного отказа, заглянув лишь на день назад, не находит её
нигде — файл дня посередине пуст, довозка ничего в него не пишет — и
повторяет вечернее сообщение так же дословно. `LOOKBACK_DAYS = 2`
(`telegram_sink.py`) закрывает ровно этот, воспроизведённый исполнением,
сценарий: два подряд отказа и прогон на третьи сутки.

Окно намеренно узкое, а не «на всякий случай пошире». `mark <id> new`
возвращает вакансию в очередь и обнуляет счётчик попыток; если её ссылка
совпадёт с файлом дня ЗА ПРЕДЕЛАМИ окна (например, пятидневной давности),
широкое окно молча проглотило бы вручную возвращённую вакансию, и владелец не
понял бы, почему она не пришла. Сторожится и это: вакансия, чья ссылка есть в
файле старше `LOOKBACK_DAYS` суток, подавляться не должна.

Законно новые вакансии подмешиванием прежних файлов не глотаются, и
проверяется это рассуждением, а не наблюдением: вакансия, отправленная раньше
и ПОМЕЧЕННАЯ, сегодня не придёт из `unreported()` вовсе, а непомеченная —
ровно та, дубля которой мы избегаем. Прежние файлы только читаются: документ
дня собирается из содержимого сегодняшнего.

Отсюда же следует правило пустого прогона: если после дедупликации новых
вакансий нет и довозить нечего (см. ниже), приёмник **не обращается к
Telegram вовсе** и возвращает 0. Без этого при `interval_hours: 4` канал
получал бы шесть пустых сводок в сутки, и владелец перестал бы их читать — то
есть сводка потеряла бы смысл ровно тогда, когда стала бы регулярной.

**Довозка документа предыдущих суток, если он застрял.** Прежняя редакция
останавливалась на «файл дня накопительный, следующий прогон отправит его
целиком» — и это было верно только НАПОЛОВИНУ: следующий прогон СУТОК
действительно довозит целиком, но лишь если в те же сутки появится хоть одна
свежая вакансия. Пустых суток без единой новой находки не бывает не всегда, и
до появления следующей свежей вакансии документ, который сообщение уже
анонсировало, мог не доехать сколько угодно долго. Поэтому: если после
дедупликации свежих вакансий нет, но хотя бы одна из ПРИШЕДШИХ нашлась ТОЛЬКО
в файле одних из `LOOKBACK_DAYS` предыдущих суток (а не в файле суток
текущих), это и есть след недоставленного `send_document` — `emit` отправляет
документ РОВНО тех суток и возвращает 0, а `send_message` не трогает вовсе:
он уже ушёл тогда, и повтор был бы ровно тем дублем, которого избегает
дедупликация. Если довозка тоже падает, исключение поднимается как есть —
следующий прогон обязан попробовать снова, а не смолчать. После успешной
довозки вакансии помечаются отправленными (`report()` делает это для ВСЕХ
вакансий партии, раз ни один приёмник не упал), поэтому в норме этот путь
срабатывает один раз, а не при каждом прогоне.

Порядок внутри `emit` — **черновик на диск → `send_message` → `os.replace` →
`send_document`.** Публикация файла дня (`os.replace`) стоит МЕЖДУ двумя
отправками, и это четвёртая редакция. Первая требовала писать файл до
отправок, вторая — после обеих, третья — обычную запись между ними. Все три
были неверны, каждая по-своему, и все три ошибки нашлись исполнением, а не
чтением.

Дедупликация читает файл дня — отсюда всё остальное.

**Почему не «файл, потом отправки».** Упавшая отправка оставляет вакансии УЖЕ
вписанными: следующий прогон приносит их снова (`mark_reported` не вызывался),
дедупликация находит их в файле, `emit` возвращает 0 и **не отправляет ничего
никогда**. Одна сетевая ошибка молча съедала бы порцию вакансий.

**Почему не «обе отправки, потом файл».** Отправок две, и между ними та же дыра
с обратным знаком: `send_message` уходит, `send_document` падает, файл не
записан — следующий прогон видит вакансии новыми и шлёт **то же сообщение
второй раз**. Отказ `sendDocument` это рядовое сетевое событие, а не редкость.
Воспроизведено ревью Task 3.

**Почему не простая запись между отправками.** Запись сама может упасть, и это
третья находка: каталог отчётов `chmod 0o500` — и сообщение уже ушло, а файла
нет. Следующий прогон видит вакансии новыми и шлёт то же сообщение снова, и так
раз в четыре часа, пока том не починят. Прогон при этом громко `failed` (`csv` и
`markdown` падают там же), но канал получает дубль каждые четыре часа.
Воспроизведено финальным ревью: четыре подряд `emit` — четыре одинаковых
сообщения, ноль документов, `PermissionError` каждый раз.

**Почему черновик и `os.replace`.** Черновик пишется во временный файл В ТОМ ЖЕ
каталоге, что и файл дня, ДО первой отправки, а публикуется `os.replace`
после успешной `send_message`. Отсюда четыре свойства сразу:

- права и место на диске проверяются ДО сети, поэтому отказ каталога больше не
  оставляет отправленного сообщения;
- публикация атомарна — рваного файла дня не бывает вовсе, а не «редко»;
- отказ `send_message` убирает черновик и оставляет `path` нетронутым:
  следующий прогон повторяет всё целиком, и дубля нет, потому что сообщение не
  ушло;
- отказ самого `os.replace` (каталог мог стать недоступен уже ПОСЛЕ
  `send_message` — том отмонтировали или права сменили посреди прогона)
  тоже убирает черновик и поднимает исключение как есть: черновик не имеет
  права остаться, а `path` — не имеет права оказаться наполовину опубликован;
- отказ `send_document` застаёт файл уже опубликованным: следующий прогон
  вернёт 0 и сообщение не повторит. Цена — документ за тот прогон не придёт
  сразу же, но не бесследно: следующий прогон, у которого нет ни одной новой
  вакансии, всё равно ДОВЕЗЁТ именно этот файл документом (см. выше). Сообщение
  с «Топом» читатель получил в любом случае.

Тот же каталог — не мелочь: `os.replace` атомарен только внутри одной файловой
системы, а каталог отчётов это смонтированный том.

Дубль остаётся возможен ровно в одном случае: процесс убит между успешной
`send_message` и `os.replace`. Окно — доли миллисекунды, и размен здесь
сознателен: видимый дубль в канале против невидимой потери.

**Черновики не имеют права накапливаться в каталоге отчётов.** Два независимых
источника мусора: `os.replace` может упасть (см. пункт выше — черновик
убирается), а процесс может быть убит (`SIGKILL`, OOM) РОВНО между `mkstemp` и
`os.replace` — то есть до того, как код успеет что-либо убрать. Первое лечится
в момент отказа; второе, по определению, не может лечиться в том же процессе,
который убит. Поэтому `emit` в НАЧАЛЕ каждого вызова подчищает черновики,
оставшиеся от прошлых прогонов (`*-new.html*.part` в каталоге отчётов), —
раньше собственного `_draft()`. Это безопасно ровно потому, что `emit`
вызывается под общим замком прогона (`single_run`): пока идёт этот вызов,
другой процесс с тем же каталогом не работает, а значит черновик, уже
лежащий здесь на входе, не может принадлежать никому живому.

Отказ САМОЙ уборки глушится (`OSError` подавляется, черновик остаётся до
следующего прогона). Иначе она заводит новый класс отказа там, где его не
было: каталог отчётов `0o500` с осиротевшим `.part` внутри ронял даже пустой
прогон — тот, что без уборки не касался ни сети, ни диска и возвращал 0.
Черновик это мусор, а не данные, и его уборка не имеет права быть дороже
прогона.

Документ отправки собирается в памяти (существующее содержимое файла плюс новые
записи), и в `send_document` уходят ТЕ ЖЕ байты, что записаны в черновик, —
отправленное и опубликованное совпадают байт в байт по построению.

Чтение файла дня остаётся терпимым к битым байтам (`errors="replace"`), хотя
атомарная публикация рваного файла не оставляет: том переживает обновление
образа, и первый прогон после него может встретить файл, рваный ПРЕЖНЕЙ
версией кода. Строгий декодер ронял бы такой прогон и каждый следующий до смены
суток.

## §6. Формат HTML-файла

Один самодостаточный файл без внешних ресурсов: разметка и стиль внутри,
`<meta name="viewport">` для телефона, `charset=utf-8`. Ни одной ссылки на
внешний CSS или шрифт — файл открывается с диска телефона, часто без сети.

Структура повторяет markdown-отчёт, чтобы два отчёта не разошлись в смысле:
заголовок с датой, «Топ» по кластерам с началом описания у каждой вакансии,
«Остальное» одной строкой. Ссылки — теги `<a>` на `hh.ru/vacancy/<id>`.

Выжимка описания — не украшение: HTML это тот отчёт, который владелец читает с
телефона ВМЕСТО markdown (§0), и без выжимки он был бы строго беднее того, что
заменяет. Ровно поэтому обрезка и нормализация текста работодателя (длина
выжимки, управляющие и двунаправленные символы) живут в общем `sinks/text.py`, а
не двумя копиями: разошлись бы копии — разошлись бы и отчёты, то есть случилось
бы именно то, от чего этот раздел предостерегает.

В файл идут ВСЕ вакансии дня, включая попавшие в «Топ» сообщения. Отчёт, из
которого вырезан верх, читать неудобно, а дублирование здесь ничего не стоит.

Экранирование `&`, `<`, `>` во всех текстовых полях обязательно: заголовки
вакансий приходят от работодателя и содержат что угодно («C++», «R&D» — оба
встретились в прогоне 2026-07-29).

Значение атрибута `href="..."` экранируется ОТДЕЛЬНОЙ функцией (`escape_attr`),
чистящей вдобавок кавычку: `escape_html` обрабатывает только содержимое
элемента, где кавычка не опасна. Сегодня недостижимо — `url` собирается из id,
прошедшего `^/vacancy/([1-9][0-9]{0,14})$`, — но зависеть от этого факта
означало бы держать защиту вёрстки на honor system чужого валидатора.
Экранирование не имеет права испортить `VACANCY_HREF_RE`: тот читает ссылки
для дедупликации, и ложное несрабатывание означало бы дубль в канале, а не
только кривую вёрстку.

## §7. Сторожа

Тесты идут без сети, на подставном транспорте. Сторожатся свойства, которые
ломаются тихо:

1. **Токена нет ни в тексте исключения, ни в логах** — и при отказе, и на
   УСПЕШНОМ запросе. Второе важнее и было пропущено: `httpx` пишет
   `HTTP Request: POST <URL> "200 OK"` на каждый успешный запрос, а при отказе
   транспорта этой строки не существует вовсе, потому что httpx пишет её ПОСЛЕ
   получения ответа. Сторож, гонявший только `ConnectError`, был зелен
   вакуумно. Поэтому тест поднимает `httpx` до DEBUG и ищет заведомый токен в
   `data/logs/hh.log` после успешной отправки. Защиту держит не глушилка
   уровней (`QUIET_LOGGERS` снимается одной строкой в чужой отладке), а фильтр
   на ОБРАБОТЧИКАХ корневого логгера.
2. **Экранирование**: вакансия с `&`, `<`, `>` в заголовке, компании и описании
   даёт валидный HTML в файле и не ломает `parse_mode=HTML` в сообщении.
3. **Потолок 4096 в кодовых единицах UTF-16**, а не в кодовых точках: 300
   вакансий с эмодзи в заголовке дают `len(text)` = 3994 при 5494 по счёту Bot
   API. «Топ», не влезающий в лимит, обрезается с честной строкой про остаток,
   а не молча.
4. **Отказ записи файла дня не оставляет отправленного сообщения**: каталог
   отчётов `chmod 0o500` — исключение поднято, в канал не ушло ничего, мусора в
   каталоге не осталось. Плюс продолжение: после починки прав сообщение уходит
   РОВНО один раз.
5. **Дедупликация не обнуляется в полночь UTC**: отказ `send_document` в 23:50 и
   повтор в 03:50 следующих суток дают 0 и ни одного нового сообщения. То же —
   когда telegram здоров, а падает сосед. И обратная сторона: вакансия, которой
   вчера не было, в канал уезжает.
6. **Документ довозится, если он застрял, и молчит, если довозить нечего**:
   отказ `send_document` вечером, здоровая довозка следующим прогоном отправляет
   ИМЕННО тот файл документом и не трогает `send_message`. Повторный отказ
   довозки поднимает исключение, а не молчит. Обычный повтор В ТОТ ЖЕ день (файл
   суток уже содержит вакансию) довозку не запускает — иначе второй `emit` того
   же прогона слал бы документ второй раз.
7. **Окно дедупликации не обнуляется через ДВЕ полуночи**: два подряд отказа
   (вечер, затем неудачная довозка утром) и прогон на третьи сутки всё ещё
   довозят документ и не повторяют сообщение. Обратная сторона обязательна:
   вакансия, чья ссылка есть в файле СТАРШЕ `LOOKBACK_DAYS` суток, подавляться
   не должна — иначе вручную возвращённая (`mark <id> new`) вакансия молча
   потерялась бы.
8. **Черновики `.part` не остаются в каталоге ни при одном исходе, кроме
   успешного `os.replace`**: отказ самого `os.replace` убирает черновик и
   поднимает исключение; черновик, осиротевший убийством процесса между
   `mkstemp` и `os.replace` предыдущего прогона, подчищается на СЛЕДУЮЩЕМ
   `emit`, до создания собственного черновика этого вызова. И обратная
   сторона: недоступный на запись каталог с осиротевшим `.part` внутри не
   роняет пустой прогон — уборка молчит, черновик ждёт следующего.
9. **Ссылка вакансии экранируется в `href`, а `VACANCY_HREF_RE` всё равно её
   находит**: оба свойства проверяются одним тестом — ложное несрабатывание
   регэкспа означало бы дубль в канале, а не только кривую вёрстку.
10. **Одинокая запись, не влезающая в лимит целиком, не превращается в ноль
    показанных**: запасной вариант — усечённая ссылка без метаданных — влезает
    в лимит и не рвёт разметку даже на заголовке из одних `&` (пятикратное
    разбухание при экранировании).

Плюс дедупликация внутри одной пачки и внутри суток: два элемента с одним
`url` в одном вызове `emit` дают `written == 1`, а повторный `emit` того же
набора в тот же день записывает 0 и не обращается к сети.

Сторожа документа живут в `tests/test_spec_matches_code.py`: этот файл спеки не
имеет права ссылаться на код номером строки, а имена, которыми номера заменены,
обязаны существовать.

Сторожа проверяются мутацией — порча проверяемого свойства обязана красить
ровно один тест. Мутационный харнесс в этом проекте врёт дважды, поэтому
`NO_COLOR=1` и `PYTHONDONTWRITEBYTECODE=1` с чисткой `__pycache__` обязательны.

## §8. Проверка живьём

```bash
docker compose run --rm hh-search report --since 7d
```

`report_command` (`hh_search/__main__.py`) гоняет вакансии из базы через тот же
`emit_to_sinks`, что и конвейер, и **в hh.ru не ходит вовсе**. То есть проверка
канала не стоит ни одного запроса к источнику. Ссылка здесь по ИМЕНИ функции, а
не номером строки: номер съезжает от любой вставки выше по файлу и молча, без
единого красного теста (сторож — `test_telegram_spec_does_not_point_at_code_by_line_number`).

Повторять команду можно сколько угодно, но **доставит она только в первый
раз**: дедупликация идёт по файлу дня, и второй запуск находит те же вакансии
уже вписанными, поэтому в канал не уходит ничего, а на выходе стоит
`telegram: 0` с кодом 0. Это ожидаемо, а не поломка; человека об этом
предупреждает README, потому что тишина на второй проверке читается как отказ.

Шапка сообщения при этом называет «Новых вакансий: N», где N — сколько записал
этот запуск: для файла дня вакансия недельной давности новая, и счётчик честен
именно в этом смысле (§2).

## §9. Что осталось нерешённым

Отдельный порог для канала не заводится: сегодняшний `report_threshold: 60`
даёт 5 позиций из 98, и пока не на чем проверить, что каналу нужен свой. Если
после недели наблюдений окажется, что в канал идёт слишком много или слишком
мало, — это правка конфигурации, а не конструкции.

Региональный вопрос (вся Россия против удалёнки вне Нижнего Новгорода) к этому
компоненту отношения не имеет и остановлен владельцем отдельно.
