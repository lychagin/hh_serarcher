# Приёмник `telegram` — дизайн

Дата: 2026-07-29. Статус: согласован владельцем, к реализации.

Документ описывает ОДИН новый компонент. Действующее описание системы целиком —
`2026-07-27-hh-autosearch-design.md`; здесь только то, что к нему добавляется, и
только те его решения, которые новый компонент обязан соблюсти.

## §0. Откуда взялась задача

Первый живой прогон против hh.ru состоялся 2026-07-29 (прогон `id=3`, статус
`partial`): найдено 160, новых 120, отсеяно 22, обогащено и отправлено 98.
Отчёт `data/reports/2026-07-29-new.md` — 16.4 КБ, 134 строки. Владелец хочет
получать результат прогона в личный приватный канал Telegram, а не ходить за
ним на машину.

Решения владельца, принятые в этом обсуждении:

- В канал уходит «Топ» сообщением и полный отчёт файлом.
- Файл — **HTML, не markdown**: телефон не открывает `.md` браузером, и ссылки
  в нём остаются текстом. Кликабельность ссылок — требование, а не удобство.
- Первая цель — увидеть, что информация доходит. Богатство формата вторично.

## §1. Границы

Делается: приёмник `telegram` в существующей точке расширения `Sink`, рендер
HTML-отчёта, отправка сообщения и файла, сторожа.

Не делается: команды бота (канал односторонний, бот только пишет), отметка
статуса вакансии из Telegram, отдельный порог для канала, ретрай отправки
внутри прогона. Последнее — сознательно: следующий прогон повторит отправку сам,
см. §5.

## §2. Что уходит в канал

Два обращения к Bot API на прогон, в этом порядке.

**Сообщение** (`sendMessage`): строка со счётчиками прогона, затем «Топ» —
вакансии с баллом не ниже `profile.report_threshold`, каждая ссылкой на hh.ru,
с компанией, регионом, зарплатой и баллом.

В «Топ» сообщения идут только вакансии, ДОПИСАННЫЕ этим прогоном, — то есть
прошедшие дедупликацию §5, а не весь «Топ» файла дня. Иначе второй прогон суток
повторил бы в канале то, что владелец уже прочитал утром, и повторял бы это
все шесть раз в день. Файл при этом остаётся полным (§6): сообщение — про
«что нового», файл — про «что есть».

`parse_mode=HTML`, а не `MarkdownV2`. Причина фактическая: `MarkdownV2` требует
экранировать `_ * [ ] ( ) ~ \` > # + - = | { } . !`, и хотя бы один из этих
символов есть практически в каждом заголовке вакансии живого прогона («Team
Lead Go (Golang, продукты для управления инфраструктурой и PKI (TLS/ГОСТ)»,
«Backend Developer senior/middle+ (Node.js/Nest)»). В HTML-режиме экранируются
ровно три символа — `&`, `<`, `>`, — и набор разрешённых тегов (`<b>`, `<i>`,
`<a href>`, `<code>`) покрывает нужное.

Потолок `sendMessage` — 4096 символов. Сообщение строится с проверкой длины: не
влезающие позиции «Топа» отбрасываются, а вместо них дописывается строка «ещё N
— в файле». Молчаливого обрезания быть не должно: 5 позиций из 98 сегодня
укладываются с запасом, но порог — настройка, и однажды не уложатся.

**Файл** (`sendDocument`): `<ГГГГ-ММ-ДД>-new.html` из `data/reports`. Потолок
файла у Bot API — 50 МБ, потолок подписи — 1024 символа; при 98 вакансиях в
день файл занимает единицы сотен килобайт, то есть запас четырёхзначный.

## §3. Куда встраивается

Точка расширения существует с самого начала: докстринг `Sink` в
`hh_search/sinks/base.py` гласит «сюда позже встанет TelegramSink». Новый
приёмник реализует тот же протокол — `name` и `emit(vacancies, now) -> int`,
где возвращается число ЗАПИСАННЫХ, а не отданных (см. §5).

Регистрация — в `build_sinks` (`hh_search/sinks/__init__.py`) рядом с `csv` и
`markdown`. Имя в конфиге — `telegram`.

К `api.telegram.org` идёт обычный `httpx`. Вежливый клиент из
`sources/http.py` не годится и не должен использоваться: он проверяет
`robots.txt` и держит паузу `delay_between_requests_sec` под hh.ru. Применять
его к Telegram означало бы и бессмысленную проверку чужого `robots.txt`, и
паузу вежливости там, где вежливость измеряется иначе.

Рендер HTML — отдельная чистая функция, принимающая вакансии и возвращающая
строку. Отдельная потому, что её надо тестировать без сети и без Telegram, а
позже она же обслужит файловый приёмник `html`, если он понадобится. Сам
приёмник `html` сейчас НЕ делается (YAGNI): файл пишет `telegram`, потому что
именно ему есть что отправлять.

## §4. Секреты

`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` читаются из окружения. Не из YAML:
`.env` уже в `.gitignore`, уже приезжает в контейнер через `env_file` в
`compose.yaml`, и держать пароль бота в конфиге рядом с профилем поиска — значит
однажды его закоммитить. `chat_id` приватного канала отрицателен
(вид `-100…`), знак — часть идентификатора.

Отсутствие или пустота любой из двух переменных — **отказ на старте**, кодом
`EXIT_CONFIG`, до всякой сети. Это обязательство §7 основной спеки: о дефекте
конфигурации человек узнаёт до первого запроса, а не в середине прогона.
Механически это выполняется само: `build_sinks` вызывается из `_sinks()` до
`start_run()` (контракт задачи 9), и поднятая им `ValueError` уже превращается
в `EXIT_CONFIG`.

**Токен не попадает в логи.** У Bot API он лежит в ПУТИ URL
(`/bot<ТОКЕН>/sendMessage`), а проект логирует URL при отказах — то есть первая
же сетевая ошибка утащила бы пароль бота в `data/logs/hh.log`, файл, который
человек первым делом кому-нибудь показывает. Поэтому текст любой ошибки этого
приёмника строится по ИМЕНИ МЕТОДА (`sendMessage`, `sendDocument`), а URL в него
не подставляется никогда. Сторожится тестом (§7).

## §5. Дедупликация и отказ

`emit_to_sinks` (`pipeline/reporting.py`) ловит исключение любого приёмника,
записывает его в `failed` и не теряет вакансии. Но следом, в `report()`, есть
существенное для нас поведение: **при отказе ЛЮБОГО приёмника вакансии не
помечаются отправленными** (ранний возврат на строке 55) и целиком приезжают в
следующий прогон.

Файловые приёмники это переживают, потому что дедуплицируют по содержимому
файла дня. Приёмник без такой защиты выдал бы в канал дубль всякий раз, когда
упал сосед. Поэтому `telegram` дедуплицирует **тем же способом и по тому же
принципу**: файл дня `<дата>-new.html` читается перед записью, уже
присутствующие в нём вакансии считаются отправленными, `emit` возвращает число
дописанных.

Отсюда же следует правило пустого прогона: если после дедупликации новых
вакансий нет, приёмник **не обращается к Telegram вовсе** и возвращает 0. Без
этого при `interval_hours: 4` канал получал бы шесть пустых сводок в сутки, и
владелец перестал бы их читать — то есть сводка потеряла бы смысл ровно тогда,
когда стала бы регулярной.

Порядок внутри `emit`: сперва запись файла, потом отправка. Файл на диске
переживает падение сети; обратный порядок означал бы отправленное сообщение,
не отражённое в файле, и дубль на следующем прогоне.

## §6. Формат HTML-файла

Один самодостаточный файл без внешних ресурсов: разметка и стиль внутри,
`<meta name="viewport">` для телефона, `charset=utf-8`. Ни одной ссылки на
внешний CSS или шрифт — файл открывается с диска телефона, часто без сети.

Структура повторяет markdown-отчёт, чтобы два отчёта не разошлись в смысле:
заголовок с датой, «Топ» по кластерам, «Остальное» списком. Ссылки — теги `<a>`
на `hh.ru/vacancy/<id>`.

В файл идут ВСЕ вакансии дня, включая попавшие в «Топ» сообщения. Отчёт, из
которого вырезан верх, читать неудобно, а дублирование здесь ничего не стоит.

Экранирование `&`, `<`, `>` во всех текстовых полях обязательно: заголовки
вакансий приходят от работодателя и содержат что угодно («C++», «R&D» — оба
встретились в прогоне 2026-07-29).

## §7. Сторожа

Тесты идут без сети, на подставном транспорте. Сторожатся три вещи, которые
ломаются тихо:

1. **Токена нет ни в тексте исключения, ни в логах** при отказе любого из двух
   вызовов. Тест подставляет заведомый токен и ищет его подстроку в перехваченных
   логах и в сообщении исключения.
2. **Экранирование**: вакансия с `&`, `<`, `>` в заголовке и компании даёт
   валидный HTML в файле и не ломает `parse_mode=HTML` в сообщении.
3. **Потолок 4096**: «Топ», не влезающий в лимит, обрезается с честной строкой
   про остаток, а не молча.

Плюс дедупликация: повторный `emit` того же набора в тот же день записывает 0 и
не обращается к сети.

Сторожа проверяются мутацией — порча проверяемого свойства обязана красить
ровно один тест. Мутационный харнесс в этом проекте врёт дважды, поэтому
`NO_COLOR=1` и `PYTHONDONTWRITEBYTECODE=1` с чисткой `__pycache__` обязательны.

## §8. Проверка живьём

```bash
docker compose run --rm hh-search report --since 7d
```

`report_command` гоняет вакансии из базы через тот же `emit_to_sinks`
(`__main__.py:458`), что и конвейер, и **в hh.ru не ходит вовсе**. То есть
проверка канала не стоит ни одного запроса к источнику и повторяется сколько
угодно раз. Это и есть путь первой проверки «информация доходит».

## §9. Что осталось нерешённым

Отдельный порог для канала не заводится: сегодняшний `report_threshold: 60`
даёт 5 позиций из 98, и пока не на чем проверить, что каналу нужен свой. Если
после недели наблюдений окажется, что в канал идёт слишком много или слишком
мало, — это правка конфигурации, а не конструкции.

Региональный вопрос (вся Россия против удалёнки вне Нижнего Новгорода) к этому
компоненту отношения не имеет и остановлен владельцем отдельно.
