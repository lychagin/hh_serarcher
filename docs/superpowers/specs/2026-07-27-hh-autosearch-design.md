## 1. Задача

Сервис для личного использования, который регулярно ищет вакансии на hh.ru по
заданному набору листингов, отсеивает нерелевантные, оценивает оставшиеся по
профилю и присылает только новые находки.

Развёртывание — Docker-контейнер на VPS. Первая версия выгружает результаты в CSV и
Markdown; следующая добавит личный Telegram-канал.

Исходные материалы: `hh_autosearch_plan.md` (карта из 30 запросов, схема весов),
`hh_api_python_plan.md` (набросок модулей).

## 2. Ключевые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Модель работы | Инкрементальный трекер | Состояние в SQLite, на выходе только новое с прошлого прогона. Без этого Telegram-канал утонет в дублях |
| Источник данных | Листинг `/vacancies/{slug}` + JSON-LD страницы вакансии + зарплата из разметки | Публичный API закрыт, RSS-поиск запрещён `robots.txt` (см. §3). Листинг — единственный разрешённый путь |
| Глубина анализа | Двухфазная | Дешёвый отсев по заголовку, затем полное описание только для выживших |
| Оценка релевантности | Ключевые слова | LLM — заложенная точка расширения, не реализуется сейчас |
| Хранилище | Файл SQLite на volume | Один писатель, десятки тысяч строк. Postgres — оверкилл |
| Запуск | Долгоживущий контейнер | Планировщик внутри, `restart: unless-stopped`. Вся конфигурация в git |
| Форматы отчёта | CSV + Markdown | Через общий интерфейс `Sink`, к которому позже подключается Telegram |
| Telegram | Личный канал | Персональные уведомления, не переопубликация |

## 3. Исследование источника данных

### 3.1 Публичный API закрыт

```
GET https://api.hh.ru/vacancies?text=Yocto  → 403 {"errors":[{"type":"forbidden"}]}
GET https://api.hh.ru/areas/113             → 200 OK
```

403 воспроизводится при любом `User-Agent`. Поддержка API для соискателей прекращена
15.12.2025 (предупреждение на форме регистрации приложения на dev.hh.ru), токен получить
нельзя.

Проверено живьём 2026-07-27. В раунде 2026-07-28 **не перепроверялось**: в живую сеть
из этого раунда не ходим, а фикстуры ответов API не сохранялись. Практического значения
это уже не имеет: ни одна ветка кода к `api.hh.ru` не обращается.

### 3.2 Единственный разрешённый источник выдачи — курируемый листинг

`robots.txt` hh.ru закрывает любой URL с query-строкой (см. §3.5), поэтому discovery
идёт по курируемым листингам. Разрешённых форм URL ровно две; обе проверены
собственным матчером на живых правилах 2026-07-28:

| URL | Вердикт | Правило, определившее вердикт |
|---|---|---|
| `https://hh.ru/vacancies/programmist` | разрешён | не совпало ни одно правило |
| `https://hh.ru/vacancies/programmist?page=2` | разрешён | `Allow: /vacancies/*?page=` |
| `https://hh.ru/search/vacancy/rss?text=Python&order_by=publication_time` | **запрещён** | `Disallow: *?*` |
| `https://hh.ru/vacancy/135586311` | разрешён | не совпало ни одно правило |

Первая страница строится голым путём, а не `?page=0`: query-строка там не нужна, а
голый путь не совпадает вообще ни с одним правилом (`sources/listing.py`,
`build_listing_url`). Нумерация страниц у hh.ru с нуля.

Страница листинга несёт блок `<script type="application/ld+json">` с
`@type: ItemList`. Его `itemListElement` — список `ListItem`, у каждого ровно четыре
поля: `@type`, `position`, `url`, `name`. **Двадцать элементов на страницу**; проверено
на двух живых фикстурах (`listing_programmist.html.gz`,
`listing_unknown_slug.html.gz`) — в обеих ровно 20.

Что из этого следует и составляет цену переезда: **листинг отдаёт только id, url и
заголовок**. Компания, регион, зарплата и дата публикации, которые RSS отдавал сразу,
теперь приходят только со страницы вакансии, то есть на шаге обогащения.

Отвергнутая альтернатива — форма `/vacancies/{slug}?area=66&page=1`. Формально она
проходит (правило `Allow: /vacancies/*?*&page=`, проверено матчером: вердикт «разрешено»),
и она вернула бы фильтр по региону. Решение владельца: **не используется**. Query-строку
hh.ru закрыл сознательно и целиком; пролезать в неё через боковое `Allow` — соблюдение
буквы против духа. `QuerySpec.slug` отвергает символы `? & # / % ` и пробелы на старте
(`config/models.py`), чтобы такой URL нельзя было протащить и через конфиг.

### 3.3 Ограничение: 20 вакансий на страницу; пагинация есть, узких запросов нет

Пагинация разрешена явным `Allow`, поэтому окно расширяется страницами: объём
discovery равен `20 × число страниц × число листингов` и задаётся полем `pages`
(`ge=1, le=20`). Верхняя граница — вежливость, а не вкус: одна страница это один
запрос к hh.ru.

Смягчение прежней редакции — «набор из ~50 узких запросов дробит выдачу; переполнить
окно по „Yocto“ или „Buildroot“ практически невозможно» — **больше не работает.**
У hh.ru нет курируемых листингов вроде `yocto` или `embedded-linux`, и на
несуществующий slug он **не отвечает 404**: он молча отдаёт общий индекс `/vacancies`
со статусом 200 и полным `ItemList` из двадцати посторонних вакансий. Проверено на
живой фикстуре `/vacancies/yocto`: приходят кладовщик и сборщик заказов.

Отсюда два следствия, зафиксированных в коде:

1. Вместо полусотни узких запросов — несколько **широких** листингов плюс локальный
   фильтр по заголовку (`filtering/matching.py`, префильтр Task 7). Дробление выдачи
   переехало из источника в наш код.
2. Подмена листинга общим индексом обязана быть громкой. Ловится по
   `<link rel="canonical">`: сравнивается путь (у второй страницы там ещё и `?page=2`,
   поэтому именно путь, а не URL целиком) **и хост**. Без этой проверки опечатка в
   конфиге тихо заливала бы базу мусором, который потом честно обогащается, оценивается
   и попадает в отчёт — контрольный тест
   `test_only_the_canonical_stands_between_us_and_twenty_wrong_vacancies` подтверждает,
   что мусор разбирается в 20 полноценных записей.
3. **Свой хост — это `hh.ru` и его поддомены.** hh.ru отдаёт листинг с редиректом
   на региональный поддомен (`https://hh.ru/vacancies/programmist` → `302` →
   `https://nn.hh.ru/vacancies/programmist`), и тогда и `canonical`, и все двадцать
   ссылок `ItemList` ведут на поддомен. Сравнение ровно с `hh.ru` отвергало бы всю
   выдачу — на не-московском выходе discovery не работал бы вовсе. Легальность при
   этом не ослаблена: `robots.txt` кэшируется и применяется **по origin**, поэтому у
   поддомена спрашиваются его собственные правила (проверено — они совпадают с
   `hh.ru`). Соседние домены (`hh.kz`, `rabota.by`, `hh.uz`) своими **не** считаются:
   это другие сайты со своими правилами и своими id. Сравнение идёт по `hostname` с
   точкой перед суффиксом, поэтому `evil-hh.ru`, `hh.ru.evil.com` и `hh.ru@evil.com`
   чужие. Найдено контрактным тестом на живых данных, не ревью кода.

**Остаточный риск, честно.** Он вырос по сравнению с прежней редакцией:

- Пропуск. Широкий листинг сортируется не по дате публикации (управлять сортировкой
  без query-строки нечем), поэтому «окно из 20 свежих» больше не гарантировано.
  Между прогонами вакансия может выпасть за пределы просмотренных страниц и не
  попасть в базу никогда. Лечение — увеличивать `pages`, то есть платить запросами.
- Точность. Широкий листинг приносит на порядок больше нерелевантного, чем узкий
  запрос. Стоимость этого низкая (префильтр по заголовку локальный, сеть не
  задействуется), но качество отсева теперь целиком на нашем списке сигналов, а не
  на поисковом движке hh.ru. Ошибка в сигнале стоит дороже, чем раньше — см. §6.1.
- Регион. Фильтра по региону на discovery нет вовсе. Регион известен только после
  обогащения, то есть после того, как за страницу уже заплачено запросом.

### 3.4 Страница вакансии: JSON-LD плюс одно отступление

```
GET https://hh.ru/vacancy/135586311 → 200 (анонимно)
<script type="application/ld+json"> {"@type": "JobPosting", ...} </script>
```

Фактический набор полей в блоке (проверено на двух живых фикстурах, `@type` и
`@context` опущены): `title`, `description` (полный текст в HTML),
`hiringOrganization`, `jobLocation`, `applicantLocationRequirements`, `datePosted`,
`validThrough`, `identifier`. Поля `key_skills` нет; ключевые технологии извлекаются
из текста описания.

**Зарплаты в структурированных данных нет.** Поля `baseSalary` в блоке `JobPosting`
у hh.ru **не существует** — не «равно `null`», а отсутствует: в фикстуре вакансии с
явно указанной зарплатой «от 100 000 до 150 000 ₽ за месяц на руки» подстрока
`baseSalary` не встречается на странице ни разу. Проверено 2026-07-28 на
`vacancy_salary.html.gz`.

| Решение | Выбор | Цена |
|---|---|---|
| Откуда брать зарплату | Из разметки, по атрибуту `data-qa="vacancy-salary"`, одной точечной регуляркой | Сознательное отступление от принципа «структурированные данные, а не вёрстка», утверждённое владельцем. При редизайне атрибут может уехать, и зарплата потеряется для всех вакансий сразу |
| Как сделать отказ заметным | Агрегатный сторож `SalaryBlockStats` | По одной странице сказать нельзя ничего: «зарплата не указана» — обычный случай. А прогон, в котором блок не нашёлся **ни разу**, почти наверняка означает переименованный атрибут, и это уходит в лог как `WARNING` |
| Почему не HTML-парсер | Регулярка на один известный элемент | Разбирается ровно один узел, дерево страницы не трогается; зависимость на парсер не добавляется |

Разбор самой строки зарплаты («от 100 000 до 150 000 ₽») переехал в `sources/salary.py`
дословно, без изменения логики: формат совпадает с тем, что раньше приходил в RSS,
грамматика пережила пять раундов исправлений и покрыта тестами.

Всё, что даёт страница, извлекается **за один разбор** (`parse_vacancy_page`):
описание, `validThrough`, дата публикации, компания, регион, зарплата. Причина в §5.2:
за страницу заплачено одним запросом, и разъехаться этим полям нечем по построению.

### 3.5 Требование легитимности

Работаем только с публично отдаваемыми данными, без авторизации, кук и эмуляции браузера.

Утверждение первой редакции («секции `User-agent: *` нет») **неверно**. Живой
`robots.txt` hh.ru эту секцию содержит, и в ней есть `Disallow: *?*` — запрет любого
URL с query-строкой, то есть всего RSS-поиска целиком. Правила зафиксированы в
`tests/fixtures/robots_hh.txt`; вердикты §3.2 получены исполнением на этом файле.
Пользовательское соглашение hh может отдельно ограничивать автоматизированный сбор —
принятый режим работы это учитывает.

Обязательные к реализации правила:

- честный `User-Agent` с названием проекта и контактным email;
- соблюдение `robots.txt` в рантайме по RFC 9309 **собственным матчером**, а не
  `urllib.robotparser`. Причина конкретная: `RuleLine.applies_to` в стандартной
  библиотеке — это `startswith()` по `quote()`-нутому **пути без query-строки**, то
  есть подстановочный знак сравнивается как буквальный префикс. На живом файле hh.ru
  это означает, что `urllib.robotparser` разрешает и RSS-поиск, и `/resume` (правило
  `Disallow: /resume$` для неё — префикс «/resume$», которому не соответствует ни один
  реальный путь). Проверено исполнением: `can_fetch` возвращает `True` на всех трёх
  запрещённых URL. `respect_robots: true` при этом давал ложную уверенность;
- свой матчер реализует: подстановку `*`, якорь `$`, сопоставление **пути вместе с
  query-строкой**, победу самого длинного совпавшего шаблона, а при равной длине —
  победу `Allow` (RFC 9309 §2.2.2);
- **кэш правил по хостам** (ключ — origin `scheme://netloc`, а не один объект на
  клиента): иначе правила hh.ru молча применялись бы к hh.kz и rabota.by;
- **проверка на каждом хопе редиректа.** Редиректы обходятся вручную
  (`follow_redirects=False`), потому что httpx уводил бы на чужой хост молча — мимо
  robots.txt и мимо паузы между запросами. hh.ru уводит региональные вакансии на
  hh.kz и rabota.by, у которых свой `robots.txt`;
- **fail-closed при непонятном ответе на `robots.txt`.** 404 — «ограничений нет»
  (RFC 9309 §2.3.1). Любой другой не-200, сетевая ошибка, превышение числа редиректов,
  а также 200 с телом, не похожим на `robots.txt` (не `text/plain` либо начинается с
  `<` — типичная заглушка антибота), означают **полный запрет по умолчанию**. Без
  этого правила заглушка разбиралась бы как «правил нет» и давала fail-open;
- одно соединение за раз, пауза между запросами, никакой параллельности;
- соблюдение `429` и `Retry-After` (RFC 9110: и delay-seconds, и HTTP-date),
  экспоненциальный backoff, потолок ожидания 300 с, отдельная отбраковка `nan`;
- при устойчивом `403` — остановка прогона, **никаких попыток обхода**;
- условные запросы (`If-Modified-Since` / `ETag`), состояние — в таблице `http_cache`;
- вечный кэш описаний: одна вакансия скачивается ровно один раз (инвариант §5.2);
- Telegram — личный канал, персональное потребление, не переопубликация.

**Отдельное решение владельца.** Идём только легальным путём. Форма
`?area=66&page=1` не используется, хотя формально проходит под
`Allow: /vacancies/*?*&page=`: это обход духа запрета. Хаков нет и не будет; цена
решения названа в §3.3 (нет фильтра по региону на discovery).

Отвергнутые альтернативы: Playwright с залогиненной сессией и извлечение кук из Chrome.
Дают полную выдачу с пагинацией и фильтрами, но стоят браузера в образе (+700 МБ),
хрупкости к редизайну, поддержки живой сессии и куда более уверенного нарушения
соглашения. В резерв не берутся даже на случай закрытия листингов.

Модуль `sources/rss.py` **сохранён выключенным**, а не удалён. `robots.txt` — это
правила источника, а не свойство мира: если `Disallow: *?*` уйдёт, RSS вернётся как
источник discovery на порядок более богатый, чем листинг. Восстановление тогда стоит
одного вызова, а не переписывания. Конвейером модуль не используется; запрет
зафиксирован тестом на живой фикстуре правил.

## 4. Архитектура

### 4.1 Конвейер

```
1. DISCOVERY   листинги из config → /vacancies/{slug}[?page=N] → ld+json ItemList
                                  → DiscoveredVacancy (только id, url, title)
2. DEDUP       отсеять id, уже известные базе                  (обычно единицы-десятки)
3. PREFILTER   отсев по заголовку → status=rejected
4. ENRICH      GET hh.ru/vacancy/{id} → JSON-LD + разметка → описание, компания,
                                  регион, дата публикации, validThrough, зарплата
5. SCORE       Scorer.score() → score + разбивка + кластер
6. PERSIST     Repository.save() → SQLite, status=new
7. EMIT        Sink.emit() → CSV + Markdown (позже + Telegram)
```

**Объём шага 1** считается по факту: `20 вакансий на страницу × число страниц ×
число листингов`, и это же число запросов к hh.ru (`сумма pages`). Для образца
конфига из §7 (3 листинга, суммарно 6 страниц) — 6 запросов и потолок 120 записей за
прогон. Прежняя оценка «~50 запросов, ~1000 записей» относилась к RSS и больше не
применима.

Изменение шага 3: региона на этом шаге больше нет — он неизвестен до обогащения
(§3.3). Отсев идёт по заголовку, и это единственный барьер перед дорогим шагом 4.

Изменение шага 4: страница приносит теперь не только описание, но и компанию, регион,
дату публикации, `validThrough` и зарплату. Все они записываются тем же оператором,
что описание и оценка (§5.2).

Дешёвые шаги 2–3 стоят до дорогого шага 4: из сотни обнаруженных записей до
скачивания страниц доходят единицы. Низкая нагрузка на hh — следствие устройства
конвейера, а не искусственного торможения.

## 5. Модель данных

### 5.1 Схема SQLite

Приведено дословно по `hh_search/storage/schema.sql` (сверено посимвольно
2026-07-28).

```sql
CREATE TABLE IF NOT EXISTS vacancy (
    id              TEXT PRIMARY KEY,
    url             TEXT NOT NULL,
    title           TEXT NOT NULL,
    company         TEXT,
    area            TEXT,
    salary_raw      TEXT,
    salary_from     INTEGER,
    salary_to       INTEGER,
    salary_currency TEXT,
    -- NULL до обогащения: discovery идёт по листингу /vacancies/{slug},
    -- который отдаёт только id, url и заголовок. Дата публикации, как и
    -- company/area/salary, приходит со страницы вакансии. Всё, что
    -- сортировалось по этой колонке, обязано падать на first_seen_at.
    published_at    TEXT,
    -- Дата, после которой вакансия неактуальна (validThrough из JSON-LD).
    valid_through   TEXT,
    description     TEXT,
    fetched_at      TEXT,
    enrich_attempts INTEGER NOT NULL DEFAULT 0,
    score           REAL,
    score_detail    TEXT,
    cluster         TEXT,
    cluster_weight  INTEGER NOT NULL DEFAULT 0,
    primary_query   TEXT NOT NULL DEFAULT '',
    status          TEXT NOT NULL,
    reject_reason   TEXT,
    -- Машинный код причины отказа: 'prefilter' обратим, 'enrich_failed'
    -- нет. Отдельная колонка, а не префикс в reject_reason: текст
    -- причины принадлежит человеку и меняется, и разъехавшийся префикс
    -- молча изменил бы множество возвращаемых вакансий. NULL — отказ,
    -- поставленный человеком через CLI: он не возвращается.
    reject_code     TEXT,
    first_seen_at   TEXT NOT NULL,
    reported_at     TEXT,
    -- Улики: исходное значение score_detail, которое не удалось
    -- прочитать. Пишется через COALESCE (первая порча не затирается
    -- последующими) и BLOB, а не TEXT, — payload может сам быть
    -- невалидным UTF-8. Счётчика попыток рядом нет сознательно: он
    -- ограничивал сетевой цикл переобогащения, а порча оценки больше
    -- не приводит к обращениям в сеть (см. quarantine.py).
    corrupt_payload BLOB
);

-- Три состояния строки со status = 'new' различаются только парой
-- (description, score_detail) и разбираются тремя непересекающимися
-- выборками репозитория; description после первой записи не обнуляет
-- никто, поэтому страница вакансии скачивается не более одного раза.

CREATE INDEX IF NOT EXISTS idx_vacancy_status ON vacancy(status);

-- primary_query всегда переписывается тем же UPDATE, что и cluster/
-- cluster_weight (см. repository.py), поэтому в отчёте found_by_query
-- гарантированно совпадает с запросом, определившим кластер. Таблица
-- ниже хранит ПОЛНЫЙ список запросов, которыми была найдена вакансия
-- (для будущей аналитики), но репозиторий больше не выбирает
-- "победителя" из неё через недетерминированный подзапрос.
CREATE TABLE IF NOT EXISTS vacancy_query (
    vacancy_id TEXT NOT NULL REFERENCES vacancy(id),
    query      TEXT NOT NULL,
    weight     INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (vacancy_id, query)
);

CREATE TABLE IF NOT EXISTS run (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    started_at  TEXT NOT NULL,
    finished_at TEXT,
    status      TEXT NOT NULL,
    discovered  INTEGER DEFAULT 0,
    new_count   INTEGER DEFAULT 0,
    rejected    INTEGER DEFAULT 0,
    enriched    INTEGER DEFAULT 0,
    reported    INTEGER DEFAULT 0,
    -- Наблюдаемость локального цикла пересчёта: rescored — сколько
    -- оценок пересчитано за прогон, stuck — сколько вакансий осталось
    -- ждать пересчёта после него. Ненулевой stuck прогон за прогоном
    -- означает «очередь пересчёта не сходится» — это метрика прогона,
    -- а не состояние на вакансии, поэтому живёт здесь.
    rescored    INTEGER DEFAULT 0,
    stuck       INTEGER DEFAULT 0,
    -- Сколько вакансий вернулось из отказа префильтра за прогон. Правка
    -- списка стоп-слов обязана быть видимой: возврат бэклога — это
    -- работа прогона, а не тихое событие.
    requeued    INTEGER DEFAULT 0,
    error       TEXT
);

CREATE TABLE IF NOT EXISTS http_cache (
    url           TEXT PRIMARY KEY,
    etag          TEXT,
    last_modified TEXT,
    fetched_at    TEXT NOT NULL
);
```

Чего не было в первой редакции спеки, и зачем это появилось:

| Что | Назначение одной фразой |
|---|---|
| таблица `http_cache` | Валидаторы условных запросов (`ETag`, `Last-Modified`) должны переживать перезапуск контейнера, иначе `If-None-Match` бессмыслен |
| `vacancy.primary_query` | Запрос-победитель, определивший кластер: пишется тем же `UPDATE`, что `cluster`/`cluster_weight`, поэтому `found_by_query` в отчёте не может разойтись с кластером |
| `vacancy.corrupt_payload` | Улики: исходный нечитаемый `score_detail`, сохранённый как `BLOB` (сам payload может быть невалидным UTF-8) |
| `vacancy.valid_through` | `validThrough` из JSON-LD — дата, после которой вакансия неактуальна |
| `vacancy.cluster_weight` | Вес запроса-победителя: делает выбор кластера при нескольких находках детерминированным (`WHERE cluster_weight < ?`) |
| `published_at` стал nullable | Листинг даты не отдаёт: между discovery и обогащением дата публикации честно неизвестна, а подставлять правдоподобную выдумку нельзя |
| `vacancy_query.weight` | Вес каждого запроса, которым найдена вакансия: позволяет мигрирующей базе детерминированно выбрать победителя для бэкфилла `primary_query` |
| `run.rescored` | Сколько оценок пересчитано локально за прогон |
| `run.stuck` | Сколько вакансий осталось ждать пересчёта после прогона; ненулевое значение прогон за прогоном означает «очередь не сходится» |
| `vacancy.reject_code` | Машинный код причины отказа (`prefilter` / `enrich_failed`): отделяет обратимый отказ от необратимого, не заставляя разбирать человекочитаемый `reject_reason` |
| `run.requeued` | Сколько вакансий вернулось из отказа префильтра за прогон |
| индекс `idx_vacancy_status` | Все три очереди фильтруют по `status`; без индекса каждая — полный проход по таблице |

`vacancy_query` — основа для кластера и инструмент отладки конфига: показывает, какой
листинг сколько вакансий приносит и какая доля отсеивается. `run` даёт статистику по
времени и питает healthcheck.

**Миграция обязательна и реализована** (`storage/migrations.py`). Путь к базе
персистентный (том Docker на VPS), а `CREATE TABLE IF NOT EXISTS` на уже
существующей таблице не добавляет колонок — без миграции обновление сервиса означает
мёртвый сервис (`no such column` на первой же выборке). Механизм самый скучный:
спросить `PRAGMA table_info` и добавить недостающее через `ALTER TABLE ADD COLUMN`;
идемпотентно, без собственного состояния. Одно изменение так невыразимо — снятие
`NOT NULL` с `published_at`, — для него таблица перестраивается: старая отодвигается
в сторону, актуальную создаёт сам `schema.sql`, строки переливаются по пересечению
колонок. Индексы при этом сносятся явно: имя индекса в SQLite глобально, и
уцелевший старый индекс заставил бы `CREATE INDEX IF NOT EXISTS` промолчать, оставив
актуальную таблицу без индекса.

### 5.2 Жизненный цикл

```
rejected  ← префильтр отсеял (reject_code='prefilter', ОБРАТИМО),
            либо исчерпаны попытки скачивания (reject_code='enrich_failed', терминально)
new       ← вакансия в работе; ровно одно из трёх подсостояний, см. ниже
corrupt   ← прочитаны нечитаемые данные, которых нет на странице вакансии
reported  ← sink отработал успешно
interesting / applied / archived  ← вручную
```

**Отказ префильтра — единственный нетерминальный отказ, и это осознанная цена.** Первая
редакция считала `rejected` терминальным целиком: «префильтр отсеял (никогда не
скачивается)». На практике это означало, что один список `negative` обслуживает два
механизма с несопоставимой ценой ошибки — в скоринге совпадение стоит −15 очков и вакансия
остаётся в отчёте, а в отсеве то же слово означает смерть навсегда (`add_discovered`
возвращает `False`, все три выборки требуют `status='new'`). Слова образцового профиля §7
писались как ШТРАФНЫЕ признаки и в отсеве убивали целевые вакансии: «Backend-разработчик
курьерской доставки» — от `курьер`, «Разработчик CRM для отдела продаж» — от `продаж`,
«Python-разработчик HR-tech платформы для рекрутеров» — от `рекрутер`.

Решение владельца — снять необратимость, а не разводить списки. Основание: решение отсева
чисто локальное. Заголовок лежит в базе с шага discovery, компании и региона на этом шаге
нет и не будет (§3.2), значит переоценка не требует НИ ОДНОГО обращения к hh.ru. Каждый
прогон переоценивает отказы префильтра текущим конфигом и возвращает в очередь те, что
больше не совпадают (`rejected_by_prefilter()` → `requeue_prefiltered(ids)`, шаг 3
конвейера, перед отсевом — чтобы правка конфига отрабатывала за один прогон).

| Что | Как |
|---|---|
| Чем обратимый отказ отличается от необратимого | Машинным кодом `vacancy.reject_code`, а НЕ префиксом человекочитаемого `reject_reason`: текст перечисляет совпавшие стоп-слова и будет меняться, а разъехавшийся префикс молча изменил бы множество возвращаемых вакансий |
| Что возвращается | Только `reject_code='prefilter'`. `enrich_failed` значит «страница не разбирается», и заголовок этого не отменяет; ручной `mark <id> rejected` из CLI кода не имеет вовсе и не возвращается |
| Куда попадает возвращённая | `status='new'`, `enrich_attempts=0`, `reject_reason`/`reject_code` очищены → `pending_enrichment` (или `pending_scoring`, если описание уже было записано). Ровно одна из трёх выборок в любом случае |
| Почему обнуляется счётчик | Вакансия могла израсходовать попытки ДО того, как правка конфига её отбраковала. Возврат без обнуления дал бы `status='new'`, `description IS NULL`, `enrich_attempts >= max` — состояние, невидимое всем трём выборкам, то есть тот же Critical, что ниже |
| Атомарность | `executemany` + один `commit()` — одна транзакция. Смерть процесса посреди возврата (OOM-kill, `docker stop`) не оставляет половины строк возвращёнными; проверено `os._exit(1)` внутри оператора в обоих режимах журнала SQLite |
| Наблюдаемость | `run.requeued` и `INFO` со списком id |

**Цена решения, названная честно.** (1) Каждый прогон читает id и заголовок всех отказов
префильтра — локальное чтение по индексу `idx_vacancy_status`, без единого запроса к
источнику; при неизменном конфиге список возвращаемых пуст и база не меняется ни на байт.
(2) Возврат даёт странице полный бюджет попыток заново, то есть при живом 404 стоит до
`max_attempts` запросов — платится только за осознанную правку конфига и один раз.
(3) Вакансия, возвращённая и снова совпавшая со стоп-словом, будет отбракована в том же
прогоне; бесконечного цикла нет, потому что возврат отбирает ровно те строки, которые
текущий конфиг НЕ подтверждает.

**Миграция уже накопленных отказов.** У базы прошлого поколения колонки `reject_code` не
было, поэтому миграция проставляет её один раз: `reject_reason = 'enrich_failed'` (полное
равенство машинной константы, не разбор текста) → `enrich_failed`, любая другая непустая
причина → `prefilter`, отсутствие причины (ручной отказ из CLI) → код не ставится.
Накопленный бэклог считается обратимым сознательно: он как раз и состоит из вакансий,
убитых опечаткой в списке стоп-слов, и оставить его недостижимым значило бы сделать правку
конфига бесполезной там, где она нужнее всего. Бэкфилл идемпотентен (отбирает только строки
без кода) и переживает прерывание — это один атомарный `UPDATE`.

**Три непересекающиеся выборки и инвариант.** Для `status = 'new'` определены ровно
три очереди, вместе покрывающие все состояния без исключений:

| Выборка | Предикат | Что делает |
|---|---|---|
| `pending_enrichment(max_attempts)` | `description IS NULL AND enrich_attempts < max` | Единственная, ходящая в сеть |
| `pending_scoring()` | `description IS NOT NULL AND score_detail IS NULL` | Локальный пересчёт оценки, сеть не задействуется |
| `unreported()` | `description IS NOT NULL AND score_detail IS NOT NULL` | Готово к отправке |

Инвариант: **каждая новая вакансия видна ровно одной из трёх.** Предикаты
взаимоисключающие по паре `(description, score_detail)`, а `description` после первой
записи не обнуляет ни одна выборка и ни один путь обработки порчи — отсюда второй
инвариант, ниже.

Исчерпание попыток скачивания **не создаёт четвёртого, невидимого состояния**. Это
был Critical: пока `bump_enrich_attempt` и `mark_rejected` были двумя отдельно
закоммиченными шагами, между ними существовало состояние «`status = 'new'`,
`enrich_attempts >= max`», невидимое ни одной из трёх выборок — `pending_enrichment`
отсекает такую строку по счётчику, а `pending_scoring`/`unreported` по пустому
описанию. Вакансия пропадала навсегда, причём без всякой аварии: достаточно было,
чтобы конвейер не дошёл до второго вызова. Теперь лимит живёт **внутри**
`bump_enrich_attempt` и применяется тем же `UPDATE`, что инкремент: переход в
`rejected` / `enrich_failed` атомарен, и состояние недостижимо по построению, а не по
дисциплине вызывающего. Статус при этом меняется только у строки со
`status = 'new'` — терминальные `corrupt`/`reported` не воскрешаются.

**Страница скачивается ровно один раз за жизнь вакансии.** Это требование §3.5, и
именно оно определяет обработку ошибок ниже. `save_description` существует отдельно
от `save_enriched` ровно для случая «скоринг бросил исключение»: страница уже стоила
запроса к hh.ru, и терять её из-за отказа чисто локального вычисления нельзя —
вакансия остаётся в `pending_scoring` и досчитывается локально. Сериализация оценки
вычисляется до `UPDATE` по той же причине: её отказ (`PydanticSerializationError`)
раньше выбрасывал вместе с оценкой уже скачанную страницу.

Из того же требования следует, что **нечитаемое описание терминируется, а не
перекачивается**. Пустое или нестроковое `description` в JSON-LD — отказ
(`FetchFailed`) со штатным инкрементом `enrich_attempts`, а не запись пустой строки:
записанная пустота необратима, потому что обогащение выбирается по
`description IS NULL` — вакансия навсегда числилась бы обогащённой, с баллом 0 и без
единой попытки перекачать страницу. А уже записанное и позже испортившееся описание
не перекачивается: обратное решение стоит три строки, но ломает инвариант.

**Самовосстанавливающийся карантин** (`storage/quarantine.py`) разделяет порчу на два
вида, и вся разница в том, есть ли источник восстановления:

| Вид порчи | Что испорчено | Лечение | Почему так |
|---|---|---|---|
| Лечимая локально | `score` / `score_detail` | Обнулить **только** оценку → строка уходит в `pending_scoring` | Оценка вычисляется из описания, а описание в этот момент цело: пересчёт не требует ни одного обращения к hh.ru |
| Терминальная | Поля discovery (`id`, `title`, `published_at`, `salary_*`, `area`, `company`, `cluster`) или само описание | Сразу `status = 'corrupt'`, ни одна колонка не обнуляется | Перекачка их не восстановит в принципе; испорченные значения оставлены как улики, одна запись в лог |

Порядок разбора в `to_scored` значим: сначала невосстановимое, потом оценка — иначе
строку с двумя видами порчи лечили бы локальным пересчётом, который её не спасёт.
Предохранителя-счётчика в карантине нет сознательно: терминальный статус выводит
строку из всех выборок с первого раза, а локальный цикл невозможен в корне —
`ScoreBreakdown` запрещает `inf`/`nan` на входе (`allow_inf_nan=False`), то есть
нечитаемую оценку нельзя записать вовсе. Наблюдаемость на случай неизвестного
источника такой записи — счётчики `run.rescored` / `run.stuck`.

**Сохранение идёт до отправки**, а отправка выбирает из базы по `status='new'`, а не
из списка в памяти. Падение между шагами 6 и 7 не теряет данные — следующий прогон
доотправит. Хранилище не может заставить конвейер вызвать `pending_scoring()` перед
`unreported()`, но не даёт пропуску пройти незамеченным: `unreported()` сначала
считает застрявшие строки одним `COUNT(*)` по трём предикатам (не декодируя ни одного
значения, поэтому сторож не падает даже на полностью испорченной таблице) и пишет
`ERROR`, если их больше нуля.

### 5.3 Доменные модели

Сверено с `hh_search/domain/models.py`.

- `Salary` — `raw`, `amount_from`, `amount_to`, `currency`; все опциональны.
- `DiscoveredVacancy` — результат шага 1: `id`, `url`, `title`, `found_by_query`
  обязательны. `company`, `area`, `salary`, `published_at` **необязательны и на шаге
  discovery не заполняются**: листинг их не отдаёт. `published_at` необязателен
  именно поэтому, а не потому, что дата бывает неизвестна источнику — сортировки,
  опирающиеся на него, обязаны падать на `first_seen_at`.
- `VacancyDetails` — результат шага 4, всё, что даёт одна скачанная страница:
  `description` (обязательно), `valid_through`, `published_at`, `company`, `area`,
  `salary`. Компания, регион, зарплата и дата публикации лежат здесь, а не приходят
  россыпью, потому что их обязана сохранять одна транзакция вместе с описанием и
  оценкой.
- `ScoreBreakdown` — `title`, `stack`, `responsibilities`, `domain`, `penalty`,
  `total`, `matched`. `allow_inf_nan=False`: см. §5.2.
- `ScoredVacancy` — `discovered`, `details`, `score`, `cluster`.

Все — pydantic-модели. Обратное чтение из БД устроено так, что одна и та же величина
не имеет двух представлений в строке: `company`/`area`/`salary` живут в колонках
`vacancy` и приезжают через `to_discovered`, поэтому `to_details` их повторно не
читает.

## 6. Скоринг

```
score = 100 × (0.40·title + 0.30·stack + 0.20·responsibilities + 0.10·domain) − penalty
```

**title (40%)** — по заголовку, грубая шкала: 0 — ничего, 0.5 — есть роль или технология,
1.0 — есть и то, и другое.

**stack (30%)** и **responsibilities (20%)** — по полному описанию (заголовок отработан
компонентом `title` и второй раз не считается), с насыщением:
`min(найдено / целевое, 1.0)`, целевое ≈ 5 и ≈ 3 соответственно. Насыщение обязательно:
без него скоринг измеряет длину описания, а не релевантность.

**Единица счёта — ГРУППА сигналов, а не паттерн.** §6.1 обязывает перечислять написания
одной технологии отдельными паттернами (`arm`, `arm64`, `armv7`, `armv8` — правая граница
запрещает букву и цифру вплотную), и если считать их четырьмя сигналами, описание,
упоминающее одно семейство процессоров, набирает `stack = 0.8` и попадает в «Топ» наравне
с вакансией на пять разных технологий. Поэтому в конфиге написания одной сущности
собираются в группу (§7), и насыщение считает группы: одна группа — один сигнал, сколько
бы её написаний ни совпало. Простое написание — это группа из одного элемента, поэтому
профили, написанные до появления групп, читаются без правки.

**domain (10%)** — отрасль компании и контекст.

**penalty** — вычитается, а не умножается: каждый негативный сигнал стоит ~15 очков. Одно
случайное слово не убивает хорошую вакансию, три — убивают. Единица та же: три написания
одного стоп-слова — один сигнал и один штраф, а один сигнал, встретившийся и в заголовке,
и в описании, штрафуется один раз (поиск идёт по склейке обоих полей).

Разбивка сохраняется в `score_detail`, включая списки конкретных совпавших слов. В каждом
списке — по одному элементу на ЗАСЧИТАННЫЙ сигнал; если сработало несколько написаний
одной группы, они перечислены внутри элемента через ` / `. Так длина списка равна
числителю насыщения, а сам элемент по-прежнему называет слова, из-за которых сигнал
засчитан:

```json
{"title": 1.0, "stack": 0.8, "responsibilities": 0.67, "domain": 1.0,
 "penalty": 0, "total": 87.4,
 "matched": {"stack": ["Yocto", "C++", "Buildroot", "ARM / ARM64"],
             "responsibilities": ["архитектур", "код-ревью"]}}
```

Без ответа на вопрос «почему 87?» настроить веса невозможно. Округляется только `total` —
число, которое человек сравнивает с порогом; компоненты остаются как есть, иначе
арифметика выше перестаёт сходиться обратно (`0.33` вместо `1/3`).

### 6.1 Сопоставление слов (`filtering/matching.py`)

Описания на русском, наивный `keyword in text` даёт мусор. Учтено:

- **Морфология.** «разработка / разработке / разработчика» — матч по основе
  (`разработ`), а не по точной форме. `pymorphy` не берём: для полусотни слов префикс
  основы достаточен.
- **Границы слов.** `lead` не должен ловиться в `leadership`, `go` — в `google`.
- **Спецсимволы.** `C++`, `C#`, `.NET` ломают наивные регулярки, поэтому границы
  слова свои, а не `\b`: `(?<![\w+#.])` слева и `(?![\w+#]|\.\w)` справа.
- **Кириллица-латиница.** `1С` пишут и кириллической `С`, и латинской `C`; то же
  с `С++`. Без нормализации похожих символов стоп-слово молча не срабатывает.
- **Регистр и `ё`.** Нижний регистр, `ё` → `е`.

Дальше — **два жёстких следствия, выстраданных пятью раундами.** Оба означают, что
сигнал в конфиге может молча не работать, а молчание здесь стоит дороже падения:
пропущенный стоп-сигнал пропускает мусор, пропущенный позитивный — прячет хорошую
вакансию, и ни то ни другое не видно в логе.

**1. Кириллические сигналы задаются ОСНОВАМИ, а не словоформами.** Матч по основе
включается автоматически и только для слов с кириллицей без цифр (`_is_stem_word`);
для слова в конкретной словоформе основой становится вся эта форма, и косвенные падежи
не ловятся. Проверено `SignalMatcher`:

| Сигнал | «Ведущий инженер» | «вакансия ведущего разработчика» | «ведущему разработчику» |
|---|---|---|---|
| `ведущий` | совпал | **не совпал** | **не совпал** |
| `ведущ` | совпал | совпал | совпал |

То же с `старший` → `старш`, `ручное тестирование` → `ручн тестиров`. Правило: писать
`ведущ`, `старш`, `проектирован`, `архитектур` — то есть ровно ту часть, которая не
меняется. Обратная сторона правила: основа не расширяется через границу
однокоренных слов — `архитектур` не ловит `архитектор` (проверено). Такие пары
перечисляются отдельными сигналами.

**2. Латинские сигналы не префиксные, и правая граница их обрывает.** Паттерн не
срабатывает, если сразу за ним стоит буква или цифра. Проверено `SignalMatcher`:

| Сигнал | `ARM` | `ARM64` | `ARMv7` | `ARMv8` | `armv7-a` |
|---|---|---|---|---|---|
| `arm` | совпал | **не совпал** | **не совпал** | **не совпал** | **не совпал** |
| `arm64` | — | совпал | — | — | — |
| `armv` | — | **не совпал** | **не совпал** | **не совпал** | **не совпал** |
| `armv7` | — | — | совпал | — | совпал |

Отсюда: такие написания **перечисляются явно** (`arm`, `arm64`, `armv7`, `armv8`), и
«обрубок» вроде `armv` в роли префикса не работает вовсе — он не совпадает ни с чем.
Тот же случай с точкой: `node` не ловит `Node.js` (граница `(?!\.\w)` — сознательное
решение, чтобы `node` не хватал `node.js`), поэтому нужны все три написания:
`node`, `node.js`, `nodejs`. Перечисление обязательно — но считаться такое перечисление
должно за ОДИН сигнал, для чего написания одной сущности собираются в группу (§6, §7).

**3. У матча по основе есть минимальная длина — три символа.** Правило «кириллица без
цифр матчится по основе» включалось и для односимвольного слова: `negative: ["с"]`
компилировалось в `(?<![\w+#.])c\w*` и после схлопывания омоглифов совпадало с любым
словом на латинскую `c` или кириллическую `с` — проверено на живом листинге
`/vacancies/programmist`: **11 заголовков из 20** уходили в необратимый `rejected` с
правдоподобной причиной «стоп-слово в заголовке: с» в логе. То же с `по`, ловившим
«поиск», «поддержку» и «подготовку». Слово короче предела не выбрасывается, а матчится
целым словом — в конфиге написано именно оно. Правило не задевает ни латинские сигналы
(`qa`, `go`, `c++`, `c#`), ни коды с цифрой (`1c`): они и раньше матчились целым словом.
Живой сигнал `оператор пк` продолжает работать: `пк` короче предела, но фраза совпадает
и с «Оператор ПК», и с «Оператора ПК».

Списки слов компилируются в регулярки один раз при старте. Пустой или пробельный
сигнал отвергается дважды — валидатором конфига и самим `_compile`: пустой паттерн
превращается в регулярку из одних границ, совпадающую почти с любым текстом, а в
отсеве это необратимый `rejected` с пустой причиной в логе.

### 6.2 Кластер

Берётся из конфига по листингу, которым вакансия найдена. При нахождении несколькими
листингами из разных кластеров побеждает тот, у которого больше `weight`
(`WHERE cluster_weight < ?`), и `primary_query` переписывается тем же `UPDATE` —
разойтись кластеру и запросу в отчёте нечем.

### 6.3 Что попадает в отчёт

Жёсткого порога нет. В CSV идёт всё новое. В Markdown — всё новое, разделённое на «Топ»
(`score >= report_threshold`, по умолчанию 60) с выжимкой и «Остальное» одной строкой на
вакансию. Причина: при десятке новых вакансий в день порог экономит секунды чтения, но
рискует спрятать хорошую вакансию из-за неотлаженного списка ключевых слов. Раздел
«Остальное» служит обратной связью по качеству скоринга.

## 7. Конфигурация

Три файла, разделённые по частоте изменений:

```
/data/config/
  queries.yaml    # часто — набор листингов
  profile.yaml    # регулярно — сигналы, веса, стоп-слова
  app.yaml        # редко — расписание, sink'и, троттлинг
```

Все три образца ниже проверены исполнением: они проходят фактический
`load_config`, и все 67 написаний из `profile.yaml` (47 групп-сигналов)
компилируются `SignalMatcher` без исключений.

Образцы здесь и файлы в `config.example/` — **один и тот же текст**, и это
проверяется тестом (`tests/test_config_example.py`,
`test_spec_config_samples_match_config_example`), а не обещанием: два разных
«образца конфига» — это гарантированно один устаревший, причём устареет тот,
который никто не запускает. Так и вышло в прошлой редакции — §7 отставала на
семь написаний сигналов и предлагала два несуществующих slug'а.

```yaml
# queries.yaml
# Slug — это НЕ поисковый запрос: hh.ru отдаёт только курируемые листинги.
# На несуществующий slug он отвечает 200 и общим индексом (спека §3.3), а
# сторож canonical превращает это в громкий FetchFailed уже ПОСЛЕ запроса —
# поэтому каждый свой slug подтверждайте одним GET заранее.
# Проверено 2026-07-28: перечисленные ниже существуют.
queries:
  - slug: programmist
    cluster: backend
    weight: 8
    pages: 3
  - slug: razrabotchik
    cluster: backend
    weight: 8
    pages: 3
  - slug: lead-developer
    cluster: lead
    weight: 10
    pages: 1
  - slug: rukovoditel-komandy-razrabotki
    cluster: lead
    weight: 10
    pages: 1
  - slug: devops
    cluster: infra
    weight: 5
    pages: 1
```

Схема `QuerySpec` — четыре поля: `slug` (обязательно), `cluster` (обязательно),
`weight` (по умолчанию 5, `ge=0`), `pages` (по умолчанию 1, `ge=1, le=20`). Блока
`defaults` в схеме нет; `QueriesConfig` содержит только список `queries`
(`min_length=1`).

Полей `text`, `area`, `experience`, `employment`, `schedule`, `period` больше нет: они
были query-строкой, а query-строка запрещена (§3.5). Их удаление **намеренно ломает
старые конфиги** через `extra="forbid"` — молча игнорируемое поле хуже отсутствующего,
потому что создаёт иллюзию работающей фильтрации. Описание RSS-запроса переехало
в `sources/rss.py` (`RssQuery`), к самому RSS, чтобы конфиг не описывал возможностей,
которых нет.

О проверке slug'ов прямо: hh.ru на несуществующий slug отвечает 200 и общим
индексом (§3.3), поэтому проверять их обязательно — своим одним `GET`, до первого
прогона. Пять образцовых проверены живьём 2026-07-28; вместе с ними проверены и
существуют `senior-developer` и `glavnyj-programmist`, а вот `programmist-python` и
`sistemnyj-administrator`, стоявшие здесь в прошлой редакции, **не существуют** —
именно они и были примером цены такой ошибки. Хорошая новость: цена теперь громкий
`FetchFailed` со сторожа `canonical`, а не тихий мусор в базе. Плохая — прогон на
этом листинге отказывает целиком.

```yaml
                     проектирован, техдолг]
  domain:      [телеком, встраиваем, embedded, [iot, iiot], микросервис]
negative: [[junior, стажёр, intern], 1c, продаж, рекрутер, ручн тестиров,
           [оператор пк, оператор call, оператор колл, оператор станка], курьер]
report_threshold: 60
```

Группы здесь не косметика. Без них описание, упоминающее одну архитектуру всеми четырьмя
написаниями, давало `stack = 0.8` (24 очка из 30) — ровно столько же, сколько вакансия на
пять разных технологий, а заголовок «Оператор ПК / оператор станка» стоил вакансии два
штрафа вместо одного.

**Сломанные сигналы прежней редакции и почему они сломаны.** Каждая правка проверена
прогоном `SignalMatcher` на живых по форме заголовках:

| Было | Стало | Что было не так |
|---|---|---|
| `ведущий` | `ведущ` | Словоформа не ловит косвенные падежи: «ведущего разработчика», «ведущему инженеру» проходили мимо (§6.1) |
| `старший` | `старш` | То же: «Старшего разработчика C++» не совпадал |
| `ручное тестирование` | `ручн тестиров` | Не совпадал ни с «Инженер ручного тестирования», ни с «ручному тестированию» — то есть стоп-слово почти не работало |
| `arm` | `[arm, arm64, armv7, armv8]` | `arm` не ловит `ARM64`/`ARMv7`: правая граница обрывается на цифре и букве. `armv` в роли префикса не работает вовсе (§6.1). Написания собраны в группу: это одна архитектура, а не четыре технологии |
| `node` | `[node, node.js, nodejs]` | `node` сознательно не ловит `Node.js` (иначе он ловил бы и лишнее), а `NodeJS` не ловит ни один из двух |
| `оператор` | `оператор пк`, `оператор call`, `оператор колл`, `оператор станка` | **Отбраковывал целевой телеком.** «Ведущий разработчик в крупный оператор связи» получал −15; проверено, что после правки этот заголовок чист, а «Оператор ПК», «Оператор call-центра», «Оператор колл-центра», «Оператор станка ЧПУ» по-прежнему отбраковываются |

Границы и валидация, которых в первой редакции спеки не было (все — в
`config/models.py` и `config/loader.py`):

- **все числовые поля имеют границы.** `delay_between_requests_sec ≥ 0.1` (ноль
  выключает вежливость, на которой держится право ходить в источник анонимно),
  `timeout_sec > 0`, `max_retries ≥ 1`, `interval_hours ≥ 1`, `enrich.max_attempts ≥ 1`
  (ноль отправлял бы вакансию в `enrich_failed`, не попытавшись),
  `saturation.* ≥ 1` (ноль даёт `ZeroDivisionError` уже **после** похода в сеть),
  `penalty_per_signal` в `[0, 100]` (отрицательный штраф превращал бы `junior` в бонус,
  а `1500` вместо `15` обнуляет любую вакансию с одним случайным стоп-словом и не
  проявляет себя ничем; у предела float отказ и вовсе прилетал `ValidationError`'ом
  изнутри `score()`, то есть после похода в сеть),
  `report_threshold` в `[0, 100]`, `sinks` непуст, `weights` суммируются в 1.0 и
  каждый `≥ 0`;
- `allow_inf_nan=False` на базовой модели: `1e400` в YAML — это `inf`, а `NaN`
  проходит сквозь любое сравнение как «истина не нарушена», в том числе сквозь
  проверку суммы весов;
- **дублирующиеся ключи YAML отвергаются** (`_UniqueKeyLoader`). Штатный YAML молча
  оставляет последнее значение — тот класс опечатки, который `extra="forbid"` поймать
  не может, потому что имя ключа правильное. Случайно продублированный `saturation:`
  внутри `profile.yaml` бесшумно выбрасывал бы половину настроек;
- **пустой сигнал в списках отвергается** — и валидатором, и матчером (§6.1); пробелы по
  краям и лишние внутри схлопываются, потому что на матч они не влияют, а в
  `reject_reason` и в разбивку уезжают как есть;
- **пустой СПИСОК сигналов отвергается** для всех пяти позитивных полей. Он ничего не
  ронял и молча обнулял свой компонент: `stack: []` навсегда держит стек на нуле (потолок
  70), `title_roles: []` — заголовок на 0.5 (потолок 80), а все пять пустых дают ровный
  ноль каждой вакансии и пустой отчёт без единой ошибки в логе. `negative: []` остаётся
  законным: профиль без стоп-слов означает «локально не отсеиваем ничего»;
- **дубликат сигнала внутри одного списка отвергается** — по НОРМАЛИЗОВАННОЙ форме, той
  самой, в которую сигнал компилируется, поэтому `yocto`, `Yocto`, ` YOCTO ` и `1c`/`1С`
  считаются одним и тем же. Повтор накручивал насыщение (`stack: [yocto] × 5` при
  `saturation.stack = 5` давал 1.0 на описании с одним словом) и штраф, а причину отказа
  заставлял врать про число различных причин («стоп-слово в заголовке: junior, junior»).
  Мотивация та же, что у `_UniqueKeyLoader`. Повтор бессмыслен и внутри группы, и между
  группами одного списка; одно написание в РАЗНЫХ полях законно (`python` — и
  `title_tech`, и `stack`: это разные компоненты формулы с разным насыщением);
- **`slug` отвергает `? & # / %`, пробелы и внешние пробелы** — чтобы запрещённый URL
  нельзя было протащить конфигом (проверено: `slug: "programmist?area=66"` роняет
  загрузку).

### 8.2 Docker

```yaml
services:
  hh-search:
    build: .
    restart: unless-stopped
    env_file: .env
    volumes:
      - ./data:/data
    environment:
      TZ: Europe/Moscow
    healthcheck:
      test: ["CMD", "python", "-m", "hh_search", "healthcheck"]
      interval: 15m
      retries: 3
```

Образ — `python:3.12-slim`, запуск от непривилегированного пользователя, без браузеров.
Точка входа — `serve`: планировщик спит и раз в `schedule.interval_hours` (по умолчанию
4) вызывает ту же функцию, что и `run --once`.

**Размер образа: 220 МБ, а не ~150 МБ.** Ориентир первой редакции был недостижим
арифметически. Замер 2026-07-28 (`docker images`, колонка DISK USAGE):

| Образ | На диске | Сжатое содержимое |
|---|---|---|
| `python:3.12-slim` без единой правки | 177 МБ | 43.2 МБ |
| Многостадийная сборка проекта (зависимости в builder, `--target /install`) | 220 МБ | 52.7 МБ |

То есть база уже больше желаемого потолка, а весь проект с `httpx`, `pydantic`,
`PyYAML` и `typer` добавляет к ней 43 МБ. Запись «~150 МБ» была желаемым, а не
измеренным; заменена фактом.

**Три ловушки развёртывания, каждая проверена исполнением 2026-07-28.** Все три —
про то, что «настроено правильно» и «работает» здесь не одно и то же:

1. **Непривилегированный пользователь + примонтированный хостовый каталог требуют
   совпадения uid.** Контейнер от `uid 10001` с `-v ./data:/data`, где хостовый
   каталог принадлежит `uid 1000`, падает на первой же записи:
   `PermissionError: [Errno 13] Permission denied: '/data/hh.db'`. Никакого
   «postpone до первого прогона» тут нет — это `init-db`. Решение: либо создавать
   пользователя в образе с uid хозяина каталога, либо выставлять владельца каталога
   на хосте перед первым запуском; выбор фиксируется в Task 12 и обязан попасть в
   README.
2. **`docker stop` без обработчика SIGTERM добивает SIGKILL.** Ядро не применяет
   диспозицию по умолчанию к PID 1: сигнал с `SIG_DFL` до процесса просто не
   доезжает. Замер: контейнер без обработчика — `docker stop` длится полные 10.2 с
   (весь grace period) и завершается кодом 137, то есть SIGKILL; тот же контейнер с
   `signal.signal(SIGTERM, ...)` — 0.2 с и код 0. Для сервиса с открытым
   `sqlite3.Connection` и незакоммиченным прогоном разница не косметическая.
3. **`restart: unless-stopped` НЕ реагирует на проваленный healthcheck.** Docker, в
   отличие от Swarm, контейнер по `unhealthy` не перезапускает. Замер: контейнер с
   `--restart unless-stopped` и заведомо падающим healthcheck простоял в статусе
   `unhealthy` 36 с с `RestartCount = 0` и неизменным `StartedAt`. Значит
   **healthcheck — это индикатор для мониторинга, а не механизм самолечения**: если
   нужно самолечение, healthcheck должен уметь завершить процесс, а не только
   вернуть код возврата.

`healthcheck` смотрит в таблицу `run` и падает, если последний **успешный** прогон
старше двух интервалов. Ловит сценарий «процесс жив, работа не делается» — при
условии, что за индикатором кто-то смотрит (см. пункт 3).

## 9. Обработка ошибок

| Ситуация | Реакция |
|---|---|
| Таймаут/сеть на одном запросе | `WARNING`, остальные запросы продолжаются, прогон `partial` |
| `429` + `Retry-After` | Ждём указанное время (потолок 300 с), экспоненциальный backoff, до `max_retries` попыток |
| Устойчивый `403` | `AccessForbidden`: остановка прогона, `status=failed`, громкий лог. Обходных путей нет |
| `robots.txt` запрещает URL | `RobotsDisallowed` до отправки запроса; в сообщении — правило, определившее вердикт |
| `robots.txt` недоступен или непонятен | Полный запрет по умолчанию (fail-closed, §3.5) |
| hh.ru отдал общий индекс вместо запрошенного slug | `FetchFailed` по несовпадению `<link rel="canonical">`: скорее всего, опечатка в конфиге |
| На странице листинга нет блока `ItemList` / `itemListElement` не список | `FetchFailed`: дрейф разметки |
| Элементы листинга есть, но не разобрался ни один | `FetchFailed`: смена формата. Ноль элементов на честно пустой выдаче — законный результат |
| Один элемент листинга битый | Пропускается, но всегда с причиной в `WARNING` |
| На странице нет JSON-LD `JobPosting`, либо `description` пусто/не строка | `FetchFailed`, `enrich_attempts++`; при исчерпании лимита тем же `UPDATE` — `rejected`/`enrich_failed` |
| Блок `data-qa="vacancy-salary"` не найден ни на одной странице прогона | `WARNING` от `SalaryBlockStats`: либо рынок без зарплат, либо атрибут переименован |
| >50% обогащений провалились за прогон | Громкая тревога: вероятно, hh сменил вёрстку |
| Скоринг бросил исключение | Страница сохраняется без оценки (`save_description`), вакансия ждёт в `pending_scoring`; в сеть повторно не идём |
| Данные в базе не читаются | Карантин: локально излечимая порча обнуляет только оценку, терминальная даёт `status=corrupt` (§5.2) |
| Sink упал | Вакансия остаётся `new`, доотправится следующим прогоном |
| Конфиг невалиден | Падение на старте, до сетевых запросов |

Правило про 50% — канарейка на смену формата источника: проблема обнаруживается в тот же
день, а не через месяц по пустым отчётам. Ту же роль играют громкие отказы разбора:
дрейф формата обязан отказывать, а не тихо пустеть, иначе сервис молчит месяцами при
зелёном healthcheck.

Логи — в stdout (подхватывает `docker logs`) и в `/data/logs/hh.log` с ротацией.

**Интеграционный тест конвейера** — фейковый источник, SQLite в памяти, фейковые sink'и.
Проверяет дедупликацию между прогонами, что отклонённые не скачиваются повторно, и что
падение sink'а оставляет вакансию в `new`.

**CI (GitHub Actions):** `ruff` → `mypy` → `pytest` с замоканным HTTP (`respx`). Сеть
в CI не используется — живая выдача hh сделала бы сборку флаки.

**Контрактный тест** с меткой `@pytest.mark.network` (маркер объявлен в
`pyproject.toml`, сам тест — часть Task 13, ещё не написан). Он обязан ходить в живой
hh.ru и проверять **листинг и страницу вакансии**, а не RSS:

- `/vacancies/{slug}` отдаёт блок `ld+json` с `ItemList` и непустым `itemListElement`;
- `<link rel="canonical">` на этой странице указывает на запрошенный slug;
- страница вакансии содержит `JobPosting` с непустым `description`;
- атрибут `data-qa="vacancy-salary"` находится хотя бы на одной странице из выборки;
- живой `robots.txt` по-прежнему запрещает URL с query-строкой и по-прежнему
  разрешает `/vacancies/*?page=`.

В CI пропускается (`addopts = "-m 'not network'"`), запускается вручную
(`pytest -m network`). Ранняя система оповещения об изменении источника.

**Вывод, вынесенный из этого проекта.** Тесты парсеров внешних форматов пишутся на
**живой** фикстуре, а не на придуманной. Причина не стилистическая: все три Critical и
большинство Important в этом проекте нашлись **исполнением**, а не чтением —
живой фикстурой вместо синтетической, убийством процесса, порчей базы сырым SQL,
подменой валидатора. Ни один не был виден при чтении кода, и общая их черта одна: код
разбора внешнего формата писался под воображаемые данные, а тесты — тем же человеком и
с теми же представлениями. Отсюда же правило для ревью: атаковать модуль своими
входами, а не ограничиваться чтением диффа.

## 13. Предусловия и открытые вопросы

Предусловия:

- регистрация приложения на dev.hh.ru **не требуется** — выбранный подход не
  использует авторизацию;
- контактный email для `User-Agent` задаётся в `app.yaml` при первом развёртывании;
- **каждый `slug` в `queries.yaml` проверяется одним GET перед первым прогоном**:
  hh.ru на несуществующий slug отвечает 200 и общим индексом (§3.3). Ошибка не тихая
  (сторож `canonical` даёт `FetchFailed`), но она отказывает весь листинг;
- uid пользователя в образе согласуется с владельцем хостового каталога `./data`
  до первого запуска (§8.2, пункт 1).

Что из первой редакции **снято как неактуальное**:

- справочники `experience` / `schedule` / `employment` больше не нужны: этих
  параметров нет в конфиге, они были query-строкой;
- коды регионов (`https://api.hh.ru/areas`, `66` = Нижний Новгород) на discovery не
  применяются: фильтра по региону там нет вовсе. Регион известен только после
  обогащения и используется в скоринге и отчёте.

Открытые вопросы:

1. **Чем компенсировать потерю узких запросов.** Сейчас ответ — несколько широких
   листингов плюс `pages`, то есть больше запросов и больше нагрузки на локальный
   отсев. Насколько этого хватает, покажет первая неделя реальных прогонов: метрика —
   доля `rejected` от `discovered` в таблице `run`. Если она уйдёт выше ~95%,
   конфигурацию листингов надо пересматривать.
2. **Полный список существующих курируемых slug'ов hh.ru неизвестен.** Проверен один
   (`programmist`); один проверен как несуществующий (`yocto`). Способ получить
   список без обхода запретов пока не найден — карта листингов собирается вручную,
   по одному GET на кандидата.
3. **Сортировка листинга не документирована.** Управлять ею нечем (это была бы
   query-строка), и «20 самых свежих» больше не гарантировано (§3.3). Оценить
   реальный риск пропуска можно только наблюдением: сравнить `first_seen_at` с
   `published_at` на нескольких прогонах.
4. **Самолечение при `unhealthy` не решено.** Healthcheck — индикатор, а не механизм
   (§8.2, пункт 3). Нужен ли отдельный механизм (завершение процесса из
   healthcheck, внешний watchdog) или достаточно индикатора для мониторинга —
   решается в Task 11 вместе с обработчиком SIGTERM.
