# Команды и режим работы

```bash
docker compose up -d                                  # демон по расписанию
docker compose run --rm hh-search run                 # разовый прогон
docker compose run --rm hh-search init-db             # схема базы (первый запуск)
docker compose run --rm hh-search healthcheck         # свежесть последнего прогона
docker compose run --rm hh-search report --since 7d   # перегенерировать отчёт
docker compose run --rm hh-search mark 12345 applied  # пометить вакансию
docker compose run --rm hh-search cleanup             # план уборки; --apply исполняет
```

`serve` — точка входа контейнера: спит и раз в `schedule.interval_hours`
вызывает тот же прогон, что и `run`.

## Три предохранителя против лишних запросов

**Один прогон за раз.** `run` во время работы `serve` получит «прогон уже
идёт» и код 1. Замок — файл рядом с базой, его снимает ядро, поэтому убитый
контейнер ничего после себя не запирает. Без замка два прогона задваивали
отчёт: дедупликация приёмника это чтение-правка-запись по файлу дня.

**Не чаще половины интервала.** Прогон, начатый раньше, чем через половину
`schedule.interval_hours` после предыдущего успешного, **пропускается** — к
hh.ru не уходит ничего, в лог уходит строка с тем, через сколько минут прогон
снова возможен. Без этого обычная возня с конфигом («поправил профиль —
перезапустил») стоила десятков лишних обходов за вечер.

**Устойчивый `403` останавливает всё.** Два подряд — и `serve` пишет
`/data/state/access-forbidden.stop`. Пока файл на месте, в сеть не идёт **ни
одна** команда, ни `serve`, ни `run`. Проверка стоит на обеих дверях
сознательно: пока она жила только в `serve`, предохранитель открывался самым
естественным действием человека — увидев остановленный демон, он делает `run`
(«а сейчас как?») и получает полный обход листингов. Разберитесь и удалите
файл руками. Одиночный `403` прогон не роняет: он бывает антиботом на
конкретном запросе.

## healthcheck без иллюзий

Он падает, если последний **успешный** прогон старше двух интервалов, и это
индикатор для того, кто смотрит. Docker (в отличие от Swarm) контейнер по
`unhealthy` **не перезапускает** — `restart: unless-stopped` реагирует только
на выход процесса.

Успешным считается статус `ok` или `partial` (частичная потеря работы).
`failed` — там, где работы не сделано вовсе, и таких исходов четыре:

- источник не отдал ни одной запрошенной страницы листинга (потеря сети,
  недоступный `robots.txt`, блокировка);
- страницы отданы, но вакансий не найдено ни одной;
- страницы вакансий отданы, но не разобрана ни одна — так выглядит смена
  вёрстки hh.ru;
- ни один приёмник не принял непустой отчёт (например, том смонтирован не
  туда).

Иначе и полная потеря сети, и смена вёрстки, и сутки без единого файла отчёта
выглядели бы для healthcheck успехом.

## Про `docker stop` без иллюзий

Флаг остановки проверяется МЕЖДУ прогонами, поэтому цена зависит от того, во
что вы попали:

| Когда остановили | Сколько ждать | Код |
|---|---|---|
| Демон спит между прогонами | доли секунды (замер: 0.28 с) | 0 |
| Идёт прогон и успевает закончиться за `stop_grace_period` | сколько осталось прогону | 0 |
| Идёт прогон и не успевает | весь `stop_grace_period` (30 с), потом SIGKILL | 137 |

Согласовать `stop_grace_period` с длительностью прогона нельзя: её потолок
задан `app.limits`, а сверху ограничен лишь интервалом. 137 здесь не поломка:
уже сделанное не теряется на любом исходе — каждая вакансия закоммичена своим
оператором, а строку журнала, брошенную убитым процессом, закрывает следующий
прогон.

## Вернуть вакансию в работу

Вакансию, «умершую» на скачивании (`rejected` / `enrich_failed`), возвращает
`mark <id> new`: команда обнуляет счётчик попыток и чистит причину отказа.
Если понизить `enrich.max_attempts`, уже потраченные попытки становятся
чрезмерными задним числом — такие вакансии считает счётчик `run.stalled`, и
прогон об этом кричит.

## Уборка старых данных

Ничто не удаляется само: уборка ручная, зовите её раз в несколько месяцев.

```sh
docker compose run --rm hh-search cleanup                     # что будет убрано
docker compose run --rm hh-search cleanup --apply             # описания и журнал
docker compose run --rm hh-search cleanup --reports --apply   # плюс файлы отчётов
```

Без `--apply` команда ничего не трогает. Сроки по умолчанию: описания 90 дней,
журнал прогонов 365, файлы отчётов 90 (`--descriptions-days`, `--runs-days`,
`--reports-days`).

Что знать до первого запуска:

- **описания убираются, строки вакансий — нет.** Строка остаётся
  дедупликацией: удали её, и вакансия будет найдена заново, скачана ещё раз и
  повторно прислана в Telegram;
- вместе с описанием уходят его производные — вектор и выписанные моделью
  факты: пережившая исходник производная ничем не перепроверяется;
- **`report --since` за границу хранения описаний не покажет.** Команда
  предупредит об этом сама;
- **файлы отчётов удаляются только с `--reports`** — это единственное
  необратимое из трёх действий;
- файлы окна довозки Telegram не удаляются никогда: удалённая отметка `.sent`
  означает «документ застрял», и следующий прогон отправит его повторно.
